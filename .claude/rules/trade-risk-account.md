# 交易 · 风控 · 账户 专项规则

> 通用检查见 `audit.md`，后端深度见 `audit-backend.md`。
> 本规则**补上此前的覆盖空白**：`audit-strategy.md` 只管策略、`audit-backend.md` 是通用层，**交易/风控/账户三个模块此前无专项规则**（2026-09-15 新增）。
> 风控规则清单以 `docs/02-功能设计/风控模块/风控规则设计.md`（19 条）为准，本文件**不复制**。

## 一、执行链路（`modules/trade`）

### 1.1 执行开关的真相源（⚠️ 最高危的配置漂移点）

| 开关 | 位置 | 真实作用 |
|:---|:---|:---|
| `SIMULATED_TRADING` | `.env` | ⚠️ **只影响日志与 API 返回值展示**，不是执行开关 |
| `simulated_trading` | `config.yaml` → `modules.trade` | **真正的执行开关**（`modules/trade/__init__.py:78`） |

- **两者可背离**，改一个不影响另一个 → 变更任何一个都必须**同时检查另一个**
- ⚠️ **禁止**在任何文档/日志/注释中声称「置 false 就产生真实交易」——

### 1.2 系统不具备自动下单能力（勿误解，勿美化）

- 执行开关确实切换执行路径（模拟内存成交 ←→ 调 `broker_adapter.send_order`），**但两条路径的 broker 都是 `SimBrokerAdapter`**（`modules/trade/__init__.py:96-106`）
- **全仓无真实券商适配器**；真实资金风险**只在人工环节**（券商下单 + 系统录入成交）
- ⚠️ 历史误解来源：`execution_engine.py` 中「模拟模式下绝不向券商发送真实订单」「[LIVE] 真实交易模式」等注释是按"能真实下单"写的 —— **改这些代码时不要沿用该叙述**

### 1.3 运行时配置变更必须留审计

- ⚠️ `TradeManager.simulated_trading` 可被 `update_trading_config()` **运行时修改且无审计**（`modules/trade/managers/trade_manager.py:44-47`）
- **新增/修改任何运行时配置入口** → 必须写审计日志（谁、何时、把什么从什么改成什么）

### 1.4 资金死锁防护

- **满仓买入必须配「卖出用 broker 实际持仓数量」**，否则 broker 缩减过数量时卖出被拒 → 资金不释放 → 后续买入死锁
- 检查点：卖出信号的数量来源是否为 broker 实际持仓，而非策略自维护的 shares

## 二、信号状态机

- [ ] **单行流转**：同一信号不得出现「双行割裂」（落库校验 + 时间戳闭环），三阶段重构的约定不得回退
- [ ] **T+1 守卫**：判据是 `fill_date == 当日` —— ⚠️ **任何"每日重建"的数据结构都不得补 `fill_date`**，否则守卫每天恒成立 → **实盘永久冻结**（F2 教训，曾引入过回归）
- [ ] **双真相源**：`positions` 与 `signals` 的状态必须明确谁是真相源、谁负责对账；禁止两处各自演进
- [ ] 状态流转的每一步都要有可追溯的时间戳（候选 → 信号 → 订单 → 成交 → 持仓）

## 三、风控（`modules/risk`）

- 规则清单以 `docs/02-功能设计/风控模块/风控规则设计.md`（19 条：阈值 / severity / 动作 + 双层检查流程）为准
- [ ] ⚠️ **改了规则必须验证「是否真的在拦」** —— 规则存在 ≠ 生效（反例：回测侧对风控引擎是**零调用**；规则未启用时实际不拦截，见 `docs/review/17` §1-4）
- [ ] 新增风控规则必须补一条「该规则会拦截什么」的用例，否则无法证明它生效
- [ ] 订单级拒绝与账户级拒绝必须可区分（拒绝原因要落到日志，不能只返回通用失败）

## 四、账户（`modules/account`）

- [ ] **日终结算幂等**：同一交易日重复执行不得重复计提
- [ ] **`allocated_capital` 与账户权益同步**：非组合 live 策略的 sizing 基准由日终任务按绑定账户权益同步（B1 修复 `f506283`），改动该链路需回归验证「单独跑也能复利、回撤时也减仓」
- [ ] **幽灵持仓**：`PositionRepository` 的主读取方法 `include_zero` 默认 `False` 是**有意设计**，**勿当缺陷"修复"**（`docs/review/17` §0-4）
- [ ] 结算失败必须 rollback + 日志，不得静默吞掉

## 五、配置漂移审计（2026-09-15 新增）

变更 `config.yaml` / `.env` 时必须核对：

- [ ] **双开关背离检查**：`SIMULATED_TRADING`（.env）与 `simulated_trading`（config.yaml）值是否一致；不一致时**以 config.yaml 为准**并在提交信息里说明
- [ ] **废弃键检查**：所改的键是否仍有代码在读取？（用 grep 全仓搜索键名，勿凭记忆）
- [ ] **默认值陷阱**：代码里的 `config.get(key, default)` 默认值是否与 `.env`/`config.yaml 的意图一致（反例：`config.get("simulated_trading", True)`）
- [ ] **模块开关联动**：禁用某模块（`modules.<name>.enabled`）后，依赖它的日终任务是否仍会执行并报错
- [ ] ⚠️ **严禁**向 `.env` / `.git/` / 凭证文件写入任何内容（`.claude/settings.json` 有 hook 拦截）

## 六、禁止项

- **严禁** 在代码/文档/日志中把「模拟开关」表述为资金安全兜底 —— 真实风险在人工环节
- **严禁** 硬编码 DB 口令/Token（已知遗留 `etf/bottom_strategy.py:76-78`，**新代码不得复制该形态**）
- **严禁** 运行时配置变更不留审计
- **严禁** 卖出数量取自策略自维护 shares 而非 broker 实际持仓（资金死锁根因）
- **严禁** 为「每日重建」的持仓字典补 `fill_date`（T+1 守卫永久冻结）
