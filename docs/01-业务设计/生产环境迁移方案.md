## 二、环境隔离方案

### 2.1 目标架构

```
┌─────────────────────────────────────┐
│             开发环境                 │
│  IDEA 进程 :8080                    │
│  DB: quant_signals_dev              │
│  策略: 可编辑、可回测               │
│  风险: 不影响任何实盘                │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│             生产环境                 │
│  独立进程 :8081                     │
│  DB: quant_signals                  │
│  策略: running 实例代码冻结          │
│  模型: 手动升级，不自动覆盖          │
│  SIMULATED_TRADING=true（安全锁）    │
└─────────────────────────────────────┘
```

### 2.2 数据库隔离

| 维度 | 开发库 | 生产库 |
|:---|:---|:---|
| 库名 | `quant_signals_dev` | `quant_signals` |
| 用途 | 策略开发、回测、训练 | 实盘运行、信号记录、绩效跟踪 |
| `strategies` | 可编辑 | running 实例代码锁定 |
| `strategy_templates` | seed 自动更新 | seed 自动更新 |
| `factor_data` | 开发训练用 | 实盘预测用 |
| 市场数据 | 共享（同一数据源同步） | 共享 |
| `signals` | 回测信号 | **实盘信号 = 核心资产** |
| `trades` | 模拟交易 | **真实成交 = 核心资产** |

### 2.3 策略代码隔离

```
开发改了 .py 文件:
  开发库 strategy_templates → 自动更新（重启 seed）
  生产库 strategy_templates → 也更新了 ← 这是 OK 的，模板就是该最新
  生产库 strategies.code → 不更新 ← 实盘策略用创建时的快照

实盘策略升级流程:
  1. 开发环境验证（回测 OK）
  2. 在生产库新建策略实例（从最新模板创建）
  3. 生产库回测确认
  4. 旧实例 → paused, 新实例 → running
  5. 观察 1-2 周
  6. 稳定后删除旧实例
```

### 2.4 模型文件隔离

```
开发环境:
  训练模型 → modules/storage/models/etf_bottom_v2_xxx.joblib
  回测验证 OK

生产环境部署:
  手动复制到 storage/models/etf_bottom_v2_xxx.joblib
  策略 _find_latest_model() 自动发现最新 ← 由文件名排序决定
  v1 备份保留 → 出问题立刻删掉新版文件，重启策略自动回退
```

### 2.5 进程隔离

```bash
# 生产环境独立启动（Windows 服务或计划任务）
cd E:\QuantitativeTrading\quant_trade\quant_server

# 方式1: 直接启动（测试阶段）
.venv\Scripts\python.exe -m quant_server.main --config config.yaml --mode production --port 8081

# 方式2: Windows 服务（正式上线后）
# 用 nssm 或 pywin32 注册为 Windows 服务，开机自启

# 方式3: 计划任务（兜底）
# 每天 8:00 检查进程，不在则启动
```

### 2.6 .env 配置

```bash
# .env（开发 — IDEA 用）
ENVIRONMENT=development
SIMULATED_TRADING=true
DEV_DATABASE__NAME=quant_signals_dev
DEV_TUSHARE_TOKEN=xxx

# .env.production（生产 — 独立进程用）
ENVIRONMENT=production
SIMULATED_TRADING=true              # ← 安全锁，永远不改
PROD_DATABASE__NAME=quant_signals
PROD_TUSHARE_TOKEN=xxx
```

## 三、风险识别与缓解

### 3.1 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|:---|:---|:---|:---|
| 实盘进程意外退出 | 中 | 高 | Windows 服务 + 心跳监控 + 钉钉告警 |
| 数据库连接断开 | 低 | 高 | 连接池自动重连 + 超时重试 |
| Tushare 数据延迟/缺失 | 中 | 中 | 因子缓存容错（缺失值填 0）+ 补数据脚本 |
| 因子数据不一致（开发/生产） | 低 | 中 | 同一数据源同步，开发/生产用相同的 Tushare Token |
| 模型文件误删 | 低 | 高 | v1 备份永存 + v2 双份存储（modules/storage + storage） |
| `_find_latest_model` 加载错误模型 | 低 | 高 | v2 文件名含日期，手动部署，不在生产环境训练 |

### 3.2 策略风险

| 风险 | 概率 | 影响 | 缓解措施 |
|:---|:---|:---|:---|
| 策略实盘与回测偏差大 | 中 | 高 | 每周对比实盘 vs 回测净值偏差，超 2σ 告警 |
| 单策略连续亏损 | 中 | 中 | ATR 动态止损自动收紧 + 手动暂停策略 |
| 两个策略同时满仓 | 低 | 低 | 标的隔离（ETF vs 股票），额度独立 |
| 策略参数被前端误改 | 低 | 高 | running 策略前端"编辑"按钮灰掉 |

### 3.3 人为风险

| 风险 | 概率 | 影响 | 缓解措施 |
|:---|:---|:---|:---|
| 开发环境误连生产库 | 低 | 高 | .env 中用不同 DATABASE__NAME，启动时打印当前库名 |
| 生产环境 SIMULATED_TRADING 误改为 false | 极低 | 极高 | 代码中硬编码检查：production 模式下强制 true |
| 策略代码未经回测直接上实盘 | 中 | 高 | SOP：新建实例必须先在开发库跑完整 5 年回测 |

## 五、监控与巡检

### 5.1 每日检查

```sql
-- 数据新鲜度
SELECT 'stock_daily', MAX(trade_date) FROM stock_daily
UNION ALL SELECT 'etf_daily', MAX(trade_date) FROM etf_daily
UNION ALL SELECT 'factor_data', MAX(trade_date) FROM factor_data
UNION ALL SELECT 'signals', MAX(created_at) FROM signals
UNION ALL SELECT 'market_state_daily', MAX(trade_date) FROM market_state_daily;

-- 策略状态
SELECT name, status, allocated_capital 
FROM strategies WHERE status = 'running';

-- 当日信号
SELECT strategy_id, COUNT(*) FROM signals 
WHERE created_at::date = CURRENT_DATE GROUP BY strategy_id;
```

### 5.2 每周检查

```sql
-- 实盘 vs 回测偏差
SELECT 
  s.name,
  sp.trade_date,
  sp.daily_return AS live_return,
  bt.total_return AS backtest_return
FROM strategy_daily_performance sp
JOIN strategies s ON s.id = sp.strategy_id
LEFT JOIN backtest_tasks bt ON bt.id = sp.backtest_task_id
WHERE sp.trade_date >= CURRENT_DATE - INTERVAL '7 days';

-- 策略运行时长（稳定性）
SELECT name, started_at, 
  EXTRACT(EPOCH FROM (NOW() - started_at))/3600 AS hours_running
FROM strategies WHERE status = 'running';
```
