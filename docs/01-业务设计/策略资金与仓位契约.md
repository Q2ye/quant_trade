# 策略资金与仓位契约（单一契约架构）

> 2026-09-01 | 目标：统一所有策略的「sizing 资本」来源与计算口径，消除单策略/组合/实盘三套割裂，让新策略照抄即可。

---

## 一、背景与问题

回测里出现的「资金不足 → 持仓不足」级联，根因不是某个策略的笔误，而是**策略 sizing 资本口径三处割裂**：

| 问题 | 现象 |
|:---|:---|
| ① 三个策略读三个不同字段 | 高波动/低吸读 `initial_capital`，ETF底部读 `available_capital` |
| ② 回测循环从不喂真实资金 | 三个字段在回测里卡在默认 100 万，broker 真实权益（会随回撤下跌）从不回传 → 回撤后策略仍按 100 万 sizing → 超买 → 资金不足 → 幽灵持仓 → 持仓不足 |
| ③ 组合两套机制并存 | 回测用 `scale_signals`（缩 quantity，方案 A），实盘用 `update_strategy_capital`（改 capital，方案 B），文档 §5 说二选一但代码两套都在 |

---

## 二、单一契约（一条铁律）

> **策略永远只通过 `BaseStrategy` 的统一访问器读资金，绝不自己 `getattr(context, 字段)`；`context` 的资金字段由「资金管理者」（回测引擎 / 组合 allocator / 实盘 execution）唯一写入。**

### 2.1 读（策略侧，统一访问器）

`BaseStrategy` 提供两个方法，所有策略统一调用：

```python
def resolve_sizing_capital(self) -> float:
    """sizing 基准 = context.total_assets（本策略被授权部署的资本）。
    兜底 initial_capital → allocated_capital 参数 → 100000。"""

def resolve_available_cash(self) -> float:
    """sizing 封顶 = context.available_capital（本策略可用现金）。"""
```

策略侧算仓位的唯一公式（`amount = min(基准 × 权重, 可用现金)`）：

```python
capital = self.resolve_sizing_capital()
available = self.resolve_available_cash()
amount = min(capital * weight, available)
shares = int(amount / price / lot) * lot
```

**契约补充（WeightSizer 禁令）**：策略必须**自算 quantity**（走 QuantitySizer），禁止依赖 `WeightSizer` 的 `available_cash` 参数——因为那读的是 `broker.cash`（共享池），组合下会旁路分配。`WeightSizer` 仅保留为兼容，组合模式不使用。

### 2.2 写（资金管理者，唯一写入方）

| 场景 | 谁写 | `total_assets` | `available_capital` |
|:---|:---|:---|:---|
| 单策略回测 | 回测引擎（match_orders 后，撮合后选股前） | `broker.total_assets` | `broker.cash` |
| 组合回测 | 回测引擎（match_orders 后，撮合后选股前） | `broker.total_assets × w_i` | `broker.cash × w_i` |
| 实盘组合 | allocator/execution（已实现） | `allocated_capital` | `allocated_capital` |

**语义钉死**：`context.total_assets` = **本策略被授权部署的资本**（单策略=全账户权益，组合=分配额，实盘=allocated_capital）。三者数值不同、语义统一。

**写字段边界**：回测同步**只写 `total_assets` / `available_capital` / `positions`，绝不覆写 `initial_capital`**（`initial_capital` 语义是「初始资金」，复用 `update_strategy_capital` 会污染它）。

### 2.3 数据流（单一方向，无反向）

```
broker（真实权益/现金/持仓）───────────── 实盘 allocator（allocated_capital）
        │  match_orders 后同步（撮合后选股前）      │  rebalance 后同步
        └──────────────┬──────────────────────────────┘
                       ▼
            context.total_assets / available_capital / positions   ← 唯一 sizing 真相源
                       │  resolve_sizing_capital() / resolve_available_cash()
                       ▼
            BaseStrategy 子类：shares = min(capital×weight, available) / price
                       ▼
                  Sizer → Broker.submit_order
```

### 2.4 已知的有意偏离（登记，非缺陷）

> 判定原则：偏离必须 **(a) 有明确理由、(b) 有兜底、(c) 在此登记**。否则一律视为缺陷。

| 策略 / 范围 | 偏离 | 理由 | 兜底 | 登记 |
|:---|:---|:---|:---|:---|
| 跨市场动量避险轮动 | `_make_entry_signal` 用 `amount = capital × weight`，**不封顶 `resolve_available_cash()`** | 轮动时序为「先卖出（broker 提前释放资金）→ 后买入」；按**陈旧现金**封顶会导致长期半仓闲置 | ① T+1 锁定持仓未卖时，策略侧 `has_t1_locked_sell` 主动跳过买入；② broker 资金校验会缩减数量 | 2026-09-12 |
| 组合模式（全策略） | `context.available_capital = account_total × 权重`（分配额，**非真实可用现金**） | 实盘**无「每策略现金账户」**，按权重拆分是唯一可用近似 | 需用真实可用现金的策略应单独跑（绑定账户后由 `strategy_capital_sync` 写账户 `available_balance`） | 2026-09-12 |

## 三、三场景处理

### 3.1 单策略回测

- 回测引擎 `run()` 每日 `match_orders` 后（开盘撮合后、策略选股前）调用 `manager.sync_backtest_account(sid, broker)`：
  - `total_assets = broker.total_assets`（当前权益，回撤后自动缩仓）
  - `available_capital = broker.cash`
  - `positions = broker 实际持仓`（反馈闭环，见 §3.4）
- 策略按 §2.1 公式 sizing：回撤后 `capital` 变小 → 仓位自动缩，不超买。

### 3.2 组合回测

- `run_composite()` 每日 `match_orders` + `allocator.rebalance` 后、`handle_bar_batch` 前，对每个策略按 allocator 权重同步：
  - `total_assets = broker.total_assets × w_i`
  - `available_capital = broker.cash × w_i`
- **废弃 `scale_signals` 的 quantity 缩放**（改为「同步 capital」单一机制 = 方案 B），但**保留 `sig.weight *= w` 一行仅供显示/日志**（QuantitySizer 不看 weight，不影响成交）。
- 策略层不感知单/组合：永远 `resolve_sizing_capital() × weight`，组合时该值已含分配权重。

### 3.3 实盘

- 沿用已有 `update_strategy_capital` / `update_allocated_capital`：写 `total_assets`（+ `available_capital`）= `allocated_capital`。
- 与回测**同一字段、同一读取路径**（`resolve_sizing_capital()`），口径对齐。

### 3.4 反馈闭环（幽灵持仓，双向对账）

- 回测引擎把 `broker 实际持仓` 同步进 `context.positions`。
- 策略在 `_run_rebalance` 开头对账 `_holdings` vs `context.positions`（**双向**）：
  1. **卖出确认**：`_exit_pending` 中的票 broker 已无 → 卖出成交，结算 PnL 移除；broker 仍有 → 跌停/停牌挂单中，保留待成交。
  2. **幽灵删除**：`_holdings` 有、broker 无（非 pending）→ 买入被拒，删除。
  3. **broker 幽灵回补**：broker 有、`_holdings` 无 → 策略丢失跟踪（跌停卖不出残留），回补。
- 效果：买卖两侧状态机对称 —— 买入拒单不再留幽灵，卖出挂单（跌停）不再失联，broker 与策略持仓始终一致。

## 六、未来新策略接入规范

1. **读资金**：只调 `self.resolve_sizing_capital()` / `self.resolve_available_cash()`。
2. **算仓位**：`amount = min(capital × weight, available)`。
3. **自算 quantity**：走 QuantitySizer，禁 WeightSizer 的 cash 路径。
4. **对账持仓**：`_run_rebalance` 开头对账 `_holdings` vs `context.positions`。
5. **不写 context 资金字段**：资金由引擎/allocator/execution 唯一写入。
