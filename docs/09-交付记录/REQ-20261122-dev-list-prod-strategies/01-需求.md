## 问题与证据

- **现象**：dev 服务（8080）`GET /quantTrade/strategy` 返回 `total: 0`；生产（8888）返回 51 条。
- **证据 1（权限）**：`quant_dev` 对 `public.strategies` 有 SELECT；`quant_prod` 对 `dev.strategies` 无权限。
- **证据 2（解析）**：`search_path = dev, public`，而 `dev.strategies` 是实体表 → 未限定表名一律命中 dev，生产表永不被查询。
- **证据 3（表分布）**：行情表（`stock_daily`/`etf_daily`/`stock_moneyflow`/`index_daily`）只在 public → 回落生效；策略/回测/账户表在 dev 有副本 → 隔离生效。
- **影响**：dev 环境无法以生产策略为参照（对比参数、复制配置、排查差异），每次都要切到生产 UI 或手写 SQL。
- **不做的后果**：dev 与生产策略体系长期"两套孤岛"，回测副本与线上实例的参数漂移无从对照。

## 目标

dev 环境的策略列表**只读合并展示**「dev 自己的策略」+「生产策略」，生产条目带只读标记，任何写操作不得作用于生产行。

## 范围

- 包含：
  - 列表接口在 `ENVIRONMENT=development` 时，除 `dev.strategies` 外，**只读查询 `public.strategies`** 并合并返回；
  - 返回体新增 `is_prod_reference: bool`（生产条目 = True）；
  - 对 `is_prod_reference=True` 的条目，**所有写接口（更新/删除/启停）一律 409 拒绝**。
- **不包含**：不改 `quant_prod`/`quant_dev` 的 GRANT；不改 search_path；不改生产环境行为（生产列表仍只查 public）；不做跨环境写同步。

## 验收标准

- AC-1：`curl "http://127.0.0.1:8080/quantTrade/strategy?page=1&page_size=100"` → `total` ≥ 51，且返回体中至少 1 条 `is_prod_reference: true`
- AC-2：`curl "http://127.0.0.1:8888/quantTrade/strategy?page=1&page_size=100"` → 返回体**不含** `is_prod_reference: true` 的条目（生产行为不变）
- AC-3：对 `is_prod_reference=true` 的 id 发起 `PUT /quantTrade/strategy/{id}` → HTTP 409，且 `public.strategies` 该行**未被修改**（前后 md5 一致）
- AC-4：`cd quant_server && .venv/Scripts/python.exe -m pytest tests/modules/test_strategy/test_strategy_list_dev_prod.py -q`（新建）→ exit 0
- AC-5：`cd quant_server && .venv/Scripts/python.exe scripts/quality/check_all.py` → exit 0

## 约束与红线

- **只读**：dev 对 public 的任何查询不得产生写入（不得出现 INSERT/UPDATE/DELETE 到 public）。
- **生产零变化**：`ENVIRONMENT=production` 时代码路径与现在逐字一致。
- **权限**：不改 GRANT；依赖已有的 `quant_dev` 对 public 的 SELECT。
- 合并分页：`total` 为两边之和（受 filter 影响），不得出现重复 id。

## 假设与未知

- 假设：`ENVIRONMENT` 可通过 `settings` 读到（已有）。
- 未知：前端是否需要为只读条目做视觉区分（灰化/禁用按钮）——本轮不做前端改动，仅返回标记字段。
- 风险：若前端不识别 `is_prod_reference`，用户仍可能点"编辑"，此时由 AC-3 的后端 409 兜底。
