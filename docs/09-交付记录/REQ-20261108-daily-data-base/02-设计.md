# REQ-20261108-daily-data-base 设计

> 阶段 S2 ｜ 前置：`01-需求.md` 已确认 ｜ 退出：契约 + 影响面 + 取舍齐全 ｜ **写法见 `docs/06-标准规范/00-2_S2设计规范.md`**
> 主设计输入：`docs/02-功能设计/市场模块/日频数据底座补全-设计文档.md`（下称「主设计」）。本文只记录**本 REQ 的落地决策与差异**，表结构、字段、起点、回填模式照抄主设计，不重复粘贴 56 张 DDL。

## 方案概述

按「**先契约、后 DDL、再 model/repo、最后同步与回填**」的垂直顺序落地：`DATA_CONTRACTS` 是唯一配置源，驱动 DDL 校验、模型映射、同步分派、回填循环与门禁；56 张表全部按主设计建表，一表一个 SQLAlchemy model、一表一个 Repository 类。同步方法放在新增的 `DailyBaseSyncProvider` 中，`DataSyncService` 通过继承获得并只在原有映射表登记路由，避免把 6,691 行的 `sync_service.py` 再撑大 3,000 行以上。

## 契约

| 项 | 内容 |
|:---|:---|
| 配置入口 | `modules/data/data_contracts.py`：`DATA_CONTRACTS: dict[DataType, DataContract]`，56 条；`DataContract` 为 frozen dataclass |
| 契约字段 | `table` / `api`（可为 tuple，如 macro_rate 的 5 个接口）/ `primary_key` / `pit_fields` / `frequency` / `backfill_mode` / `gate_mode` / `tier` / `earliest` / `partition` |
| 回填模式 | `by_date` / `by_month` / `by_range` / `by_symbol` / `full_snapshot` / `by_snapshot`（主设计 §5.2） |
| 门禁模式 | `dense` / `sparse` / `periodic` / `derived`（主设计 §6） |
| 同步入口 | 沿用 `DataSyncService.sync_market_data(data_type, start_date, end_date, ts_codes)`；新增 56 个 `DataType` 成员，值使用 snake_case 表语义名（如 `fx_daily`、`margin_detail`） |

| 错误处理 | 单日/单标的失败记 `failed` 并继续；连续失败 3 次退出该类型并保留断点；权限错误立即中止并报告 |
| 兼容性 | 只新增表与类型，不改现有 133 张表、不改现有 DataType 语义、不改现有同步入口签名 |

## 数据流与依赖

- **同步链路**：`api/handlers` → `DataSyncService.sync_market_data` → `_sync_by_data_type` → `_sync_method_map` → `DailyBaseSyncProvider._sync_*` → `TushareSource.get_*` → `Repository.bulk_upsert` → PostgreSQL。
- **回填链路**：`backfill_daily_base.py` → 读 `DATA_CONTRACTS` → 按 `backfill_mode` 生成日期/标的/快照序列 → 调 `DataSyncService` 或直接调 provider 方法 → 每批写 `data_backfill_progress` → `--verify` 做 API↔DB 计数对照。
- **门禁链路**：`check_daily_base.py` → 读 `DATA_CONTRACTS` → dense/sparse/periodic/derived 四类判据 → 输出 PASS/FAIL 与缺口清单；日终由 `modules/data/__init__.py` 调用。
- **依赖方向**：`modules/data/` → `shared/database/repositories/` → `shared/database/models/`；`modules/data/` → `shared/sources/`。未反向。
- **复用**：`BaseRepository.bulk_upsert`（`repositories/base/repository_base.py:352`）、`DataSourceFactory`、`SyncTimingLogger`、`trade_calendar` 日历过滤、现有 `_convert_records_datetime/_clean_nan_values`。不新造日期循环与 upsert 基础设施。

## 持久层落地决策

| 项 | 决策 | 理由 |
|:---|:---|:---|
| Model 文件 | 7 个领域文件：`data_models_ext_fx_fund.py`、`data_models_ext_margin_macro.py`、`data_models_ext_flow_ths.py`、`data_models_ext_futures.py`、`data_models_ext_options_bonds.py`、`data_models_ext_events.py`、`data_models_ext_overseas.py`；另 1 个 `data_models_ext_progress.py` 放回填进度 | 不改 3,000 行的 `data_models.py`；按主设计批次分组便于审查 |
| Repository | 8 个领域文件，每个文件内多个 Repository 类，**每个类只对应一张表**；另 1 个 `progress_repo.py` | 保持「一表一 Repository」的类级约束，同时避免 57 个 20 行文件 |
| 类名 | 表名去下划线 + `Repository`，如 `FxDailyRepository`、`StockMarginDetailRepository` | 与现有命名一致；编码前先 grep 确认不与既有类重名 |
| 同步方法 | 新增 `services/sync_daily_base.py` 中的 `DailyBaseSyncProvider`，`DataSyncService(DailyBaseSyncProvider)` | 56 个方法约 3,000 行，放回原文件会使其从 6,691 行涨到近 1 万行；继承是最小改动且不改变对外入口 |
| 分派 | 仍在 `sync_service.py` 的 `_sync_method_map` 登记 56 条 | 保持唯一分派入口，便于审查「类型是否真的接上」 |

### 与主设计的差异（需在 S5 复核）

1. 主设计 §5.1 写「新增 `_sync_*` 方法 + dispatch → `sync_service.py`」；本 REQ 把方法体放入 `sync_daily_base.py`，只在 `sync_service.py` 登记。理由见上表。
2. 主设计未规定 model/repo 文件粒度；本 REQ 按领域合并文件，但坚持一表一 model、一表一 Repository 类。
3. 主设计 §4.4 只给 P2 的关键列；本 REQ 在编码前增加「接口字段实调探针」任务，以实调返回补全 DDL 与契约。

## 备选方案与取舍

| 方案 | 优点 | 缺点 | 结论 |
|:---|:---|:---|:---|
| A（采纳）契约驱动 + 一表一 model/repo + 同步 provider 继承 | 配置单一真相源；类型安全；任务可拆；不撑大原文件 | 文件数仍较多；provider 继承偏离主设计落点 | ✅ |
| B 契约驱动 + 通用 upsert（不建 model/repo） | 文件最少、开发最快 | 偏离项目「一表一 Repository」规范；字段类型失去 ORM 约束；用户已否决 | ❌ |
| C 全部塞进 `sync_service.py` 与 `data_models.py` | 完全照搬主设计文字 | 单文件近万行，任务无法按 ≤3 文件拆分，回归无法归因 | ❌ |
| D 先做 3 张最小闭环再扩 | 返工风险最低 | 用户已明确一次做 56 张；且 56 张可复用同一骨架 | ❌ |

## 回滚方案

- **判定条件**：DDL 应用失败、回填造成生产库锁或磁盘告警、日终同步连续失败 3 个交易日。
- **动作 1（代码）**：`git revert` 本 REQ 的 commits；`DataType` 新增成员与路由删除后，旧功能不受影响（只增不改）。
- **动作 2（数据）**：按任务表逆序先停日终接入（`modules/data/__init__.py`），再执行 `DROP TABLE IF EXISTS` 57 张新表；不影响现有 133 张表。
- **动作 3（DDL 源）**：恢复 `create_table.sql` 至本 REQ 前版本。
- **时间窗**：DDL 与首轮回填在维护窗口内执行；回滚窗口为应用后 24 小时内。
- **数据保留**：回滚前导出 `data_backfill_progress` 与各表行数报告到 `assets/`，便于复盘。

## 环境落地（实测）

- 生产库 `quant_signals`：`quant_prod`（`PROD_DB_*`）有 DML 但**无 `public` CREATE**；`DB_*` 是 `postgres`，负责 DDL。
- 应用脚本按 `--role admin|app` 区分：`admin`（postgres）建表，`app`（quant_prod）校验。`public` 的默认 ACL 为 `quant_prod=arwd/postgres`，新建表自动获得 SELECT/INSERT/UPDATE/DELETE。
- 字段以 2026-11-08 探针（`assets/api_probe.md`）为准；与主设计 §4 的差异（如 `ths_member` 无 weight、`cb_daily` 无估值字段）已在 `03-任务.md` 偏差记录逐条列出。
- 超表：`fx_daily`、`fut_daily`、`opt_daily`、`cb_daily`、`stock_cyq_perf`、`stock_moneyflow_ext`、`index_ths_daily` 共 7 张，已实测创建成功。
