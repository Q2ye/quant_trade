> **本文件是操作手册，定义「如何做」。关于「我是谁」「核心行为准则」，请参见 `智能体提示词.md`。**

## 第一优先级：开发铁律（最高规则）

> **在执行任何编码任务之前，你必须无条件遵循以下四条规则。违反任何一条即视为工作不合格。**

### 1. 编码前先思考：先探索，后沟通，再行动
- 任何编码任务前，必须先执行 **「信息收集三件套」**：
  - ① 阅读 `docs/` 下三份设计文档（方案设计、混合架构设计、数据表设计）及项目 SQL 文件。
  - ② 浏览项目根目录结构，重点关注 `api/`、`core/`、`shared/` 和对应的 `modules/` 子目录。
  - ③ 读取相关模块的 `handlers.py`、`schemas.py`、核心引擎文件，理解现有实现。
- 遇到模糊需求、架构歧义、文档冲突时，**必须停下来向用户提问澄清**。
- **禁止**默默选择一种解释直接开始编码。
- 提问示例：
  - *“该功能在《方案设计》中归属于策略模块，但《混合架构设计》目录中未见对应路径，请问应以哪份文档为准？”*
  - *“您提到‘实时风控’，是指事前拦截还是事后告警？需要我明确后再设计事件流。”*

### 2. 简约至上：代码最简化
- 任何**过度设计**必须一目了然且能被明确质疑。
- 优先使用标准库、成熟开源方案，避免引入不必要的抽象层。
- 原则：能用一行解决的绝不写十行；能复用一个函数绝不复制粘贴。

### 3. 精确编辑：只修改必要的部分
- **严禁**顺手“修复”旁边无关代码的格式、命名或逻辑（即便它不符合规范）。
- 若发现相邻代码存在严重问题，必须先向用户报告并获得许可后方可改动。
- 输出时仅包含本次需求相关的文件变更，不掺杂无关重构。

### 4. 目标驱动：将模糊指令转化为可验证目标
- 开始编码前，必须将用户模糊需求转化为 **可验证的交付清单**。
- 示例转化：
  - 用户说：*“加一个数据清洗”* → 你应输出：*“目标：为 `market_data` 表新增 `clean_price` 字段，并在数据同步引擎中加入基于 Z-Score 的异常值过滤逻辑。验证方式：运行 `test_data_cleaner.py` 应通过。”*
- 输出代码前，先简述本次交付目标及验证方法。

## 二、工作流程（SOP）

当用户提出开发需求时，你必须严格按照以下**八步标准作业流程**执行，**不得跳过任何一步**。

### 步骤 0：知识准备（自动化信息收集）
- 加载 `docs/` 目录下的三份设计文档（方案设计、混合架构设计、数据表设计）到当前对话上下文。
- 读取项目根目录的 SQL 初始化脚本或数据库迁移文件，了解完整的表结构定义。
- 使用终端工具（如 `tree` 或 `ls -R`）列出项目根目录结构，获得 `api/`、`core/`、`shared/`、`modules/`、`utils/`、`tests/` 的完整视图。
- **目标**：在脑中还原系统的分层架构、模块边界、数据模型和当前代码实现现状。

### 步骤 1：需求定位与模块映射
1. 判断需求在核心业务流程中的位置：**数据同步 → 策略研究 → 回测验证 → 实盘交易 → 监控分析**。
2. 判断需求属于哪个业务模块：数据、策略、交易、回测、账户、分析、监控、系统。
3. 对照《方案设计》2.2.1 模块职责划分表确认模块边界，确保需求不越界。

### 步骤 2：架构合规性预检
- **检查重复**：该功能是否已在 `shared/` 或 `core/` 中实现？若有，强制复用，严禁在模块内重复造轮子。
- **检查依赖方向**：确保依赖关系是 `Modules → Shared/Core`，而非反向。
- **检查事件通信**：确认需要哪些事件，事件是否已在 `core/events/` 或模块的 `events/` 目录中定义。

### 步骤 3：开发路径规划（必须显式输出）
基于以上信息收集，**在开始编写任何代码前**，向用户提交一份 **《开发路径说明》**，格式如下：

```markdown
## 开发路径说明

### 涉及模块与文件
- 新增文件：
  - modules/xxx/engines/xxx_engine.py  （原因：实现 xxx 引擎）
  - modules/xxx/services/xxx_service.py （原因：纯计算逻辑）
- 修改文件：
  - api/routers/xxx_router.py           （原因：新增 API 端点）
  - core/events/xxx_events.py           （原因：新增事件类型 XXXEvent）
  - shared/database/repositories/xxx_repo.py （原因：新增查询方法）

### 跨模块影响评估
- 对 `core/` 的修改将影响哪些模块？是否需要同步调整？
- 对 `shared/` 的修改（如新增表、新增 Repository 方法）会被哪些服务调用？
- 新增事件类型会被哪些引擎订阅？是否产生连锁反应？

### 验证方案
- 单元测试路径：tests/unit/modules/xxx/test_xxx.py
- 关键验证点：XXX 输入 → 期望输出 YYY
- 运行命令：pytest tests/unit/modules/xxx/ -v

### 风险与待确认点
- （列出需要用户决策的模糊点，明确提问）
```
**关键铁律**：
- 如果修改涉及 `core/` 或 `shared/` 目录，**必须**在《开发路径说明》中单独列出受影响的所有模块，并给出同步修改计划。
- **严禁**跳过此步骤直接开始编码。必须等待用户回复“确认”或提出修改意见。

### 步骤 4：用户确认
- 等待用户对《开发路径说明》给出明确反馈（“可以开始”、“做以下调整后开始”等）。
- 若用户提出修改，返回步骤 3 更新计划，再次等待确认。

### 步骤 5：实施开发（按确认的计划执行）
- **目录结构**：严格按照设计文档中的 **目录结构** 放置文件。
- **基类继承**：
  - 引擎类必须继承 `core/engines/base/engine_base.py`。
  - Repository 必须继承 `shared/database/repositories/base/repository_base.py`。
  - 事件类必须继承 `core/events/base_event.py`（如果项目已定义事件基类）。
- **代码输出**：提供完整文件路径、类定义、关键方法及依赖注入示例。
- **修改禁区**：只修改《开发路径说明》中列出的文件，绝不顺手重构无关代码。

### 步骤 6：交付与验证
- 给出完整的实现后，提供验证指引：
  - 相关的测试命令（pytest、curl 等）。
  - 若为 API 接口，提供请求/响应示例。
- 若涉及数据库变更，提供 SQL 变更脚本或提醒用户运行数据库迁移。
- 主动询问用户是否需要自动生成单元测试代码（若尚未提供）。

### 步骤 7：文档追溯（可选）
- 若开发过程中发现设计文档与实现存在偏差，更新相关设计文档或提出文档修改建议。
- 确保代码中的关键设计决策有注释，尤其是对架构规则的遵守（如“此处通过事件引擎通知交易模块，避免直接调用”）。

### 步骤 8：异常处理与偏差修正流程

> **核心原则：容许偏差，不容许沉默。任何偏离预期的情况都必须被识别、分析并主动上报用户。**

开发过程中，当出现以下三类异常场景时，必须暂停执行并启动对应处理流程。

#### 场景 A：规划阶段发现信息缺失或矛盾

**触发条件**（在步骤 0~3 期间）：
- 文档之间存在不可调和的冲突，且无法通过“文档优先级”规则解决。
- 需要访问的目录或文件在项目中不存在。
- 需求的业务归属跨越多个模块边界，无法明确划分主责模块。

**处理流程**：
1. **立即停止**规划，不输出《开发路径说明》。
2. 向用户提交 **《信息澄清请求》**，格式如下： 
3. 等待用户确认修正计划后，方可继续代码编写。
```markdown
## 信息澄清请求

### 遇到的问题
（描述具体冲突或缺失信息，引用文档原文或目录位置）

### 需要澄清的内容
（列出需要用户明确回答的具体问题，提供可选项供用户选择）

### 对开发的影响
- 当前问题导致开发无法推进的阶段：规划 / 实施 / 验证
- 若无法及时解决，可能影响的时间窗口或后续任务
```
#### 场景 B：开发执行阶段发现原计划偏差

**触发条件**（在步骤 5 期间）：
- 发现已确认的《开发路径说明》存在遗漏文件或错误假设。
- 实现过程中发现现有代码结构与文档描述不一致，导致无法按计划执行。
- 需要额外修改计划外文件才能完成功能（如发现必须同时修改某个引擎基类）。

**处理流程**：
1. **立即停止**代码编写，不继续「将错就错」。
2. 向用户提交 **《偏差分析与修正计划》**，格式如下：

   ## 偏差分析与修正计划

   ### 偏差描述
  - 原计划中的假设：（引用《开发路径说明》中的具体内容）
  - 实际情况：（描述发现的不一致或遗漏）
  - 偏差根本原因：（需求理解偏差 / 架构遗漏 / 代码与文档不同步 / 其他）

   ### 影响评估
  - 已编写代码的受影响程度：（完全可用 / 需部分重构 / 需废弃重写）
  - 对《开发路径说明》的影响：需修改哪些条目
  - 对进度的影响：预计额外耗时

   ### 修正方案
  - 方案描述：（具体修正步骤）
  - 涉及的新增/修改文件列表：
    - modules/xxx/yyy.py （原因）
    - core/zzz.py （原因）
  - 修正后的验证方案是否变更：是 / 否

   ### 风险与备选方案
  - 修正方案可能引入的新风险
  - 是否存在更保守的替代方案（如先实现核心功能，后续优化）

3. **等待用户确认**修正计划后，方可继续代码编写。

#### 场景 C：用户中途调整需求或提出变更

**触发条件**（在步骤 5 或 6 期间）：
- 用户在开发过程中提出与已确认《开发路径说明》不同的新需求或修改意见。
- 用户在验证阶段（步骤 6）要求增加或变更功能。

**处理流程**：
1. **不直接开始修改**，先分析变更影响。
2. 向用户提交 **《需求变更影响评估》**，格式如下：

   ## 需求变更影响评估

   ### 变更内容
  - 原需求：（引用已确认的需求或计划）
  - 新需求：（明确变更内容）

   ### 影响分析
  - 已完成工作的受影响程度：
    - 可直接复用：列出文件
    - 需修改：列出文件及修改量（轻/中/重）
    - 需废弃：列出文件
  - 对验证方案的影响：是否需要重新设计测试用例
  - 对进度的影响：预计额外耗时

   ### 建议
  - （基于影响分析，给出推荐方案或替代方案供用户决策）

3. **等待用户确认**后，返回步骤 3，更新《开发路径说明》（标注为修订版），再按新计划执行。

#### 异常处理通用铁律
- **任何异常场景都必须显式提交用户确认**，严禁 AI 自行决定解决方案。
- **偏差文件必须存档**：所有《信息澄清请求》《偏差分析与修正计划》《需求变更影响评估》都属于本次开发对话的一部分，后续排查问题时需要追溯。
- **错误不容忍连环发生**：若同一任务出现两次以上偏差，必须发起一次 **「根因分析」**，在《偏差分析与修正计划》中增加“是否需要更新设计文档或架构规范”的建议，防止系统性偏差持续发酵。

## 三、核心架构规则（必须严守）

### 3.1 稳定层、灵活层与通信中枢
- **稳定层**（`api/`、`core/`、`shared/`）：不可被业务模块反向依赖。
- **灵活层**（`modules/`）：各模块独立，通过事件引擎通信。
- **通信中枢**（`EventEngine`）：模块间异步通信的唯一合法通道。

### 3.2 Engine（引擎）vs. Service（服务）
- **Engine**：有状态，响应事件，协调 Service。继承 `EngineBase`。
- **Service**：无状态，纯业务逻辑计算。不持有事件引擎引用。

### 3.3 通信机制
- **同步调用**：Service 调用 Repository。
- **异步通信**：模块间通信必须使用 **事件引擎 (EventEngine)**。

## 四、架构遵循与实现灵活性原则

**核心思想：宏观架构守拙，微观实现取巧。**

### 4.1 必须严格自研（遵循设计文档）
- 事件引擎：`core/engines/system/event_engine.py`
- 引擎基类与生命周期管理：`core/engines/base/`
- 模块边界与 API 网关：路由、中间件结构
- Repository 基类与模式：一表一仓库

### 4.2 优先复用优秀开源库（示例清单）
- **技术指标**：`ta-lib`、`pandas-ta`
- **数学计算**：`numpy`、`scipy`
- **回测框架**：核心事件流自研，策略执行可借鉴 `backtrader` / `vectorbt` 逻辑
- **数据处理**：`polars`、`pandas`
- **任务调度**：`APScheduler`
- **数据库驱动**：`asyncpg`、`SQLAlchemy`
