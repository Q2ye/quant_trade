# 风险管理业务流程：监控 → 告警 → 处理
整个流程分为三层闭环，由风控引擎驱动
```
┌─────────────────────────────────────────────────────────┐
│                    配置层（事前）                          │
│                                                         │
│  定义规则 → 设置阈值 → 选择动作（告警/软阻断/硬阻断）         │
│      ↑                                                   │
│      │  规则分为两级：                                     │
│      │  · 账户级规则（全局，如单日最大亏损 5%）               │
│      │  · 策略级规则（按策略，如单股最大仓位 20%）             │
│      │                                                   │
│      │  每条规则有 severity（严重度）和 action（执行动作）     │
│      │  · alert   = 仅告警，通知但不干预                    │
│      │  · soft_block = 禁止新开仓，已有仓位可平              │
│      │  · hard_block = 强制平仓，立即中断交易               │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    监控层（事中）                          │
│                                                         │
│  风控引擎持续轮询（或实时推送）：                            │
│  · 账户净值、持仓市值、回撤幅度                             │
│  · 策略盈亏、交易次数、持仓天数                             │
│                                                         │
│  每轮检查：当前值 vs 规则阈值                               │
│  ├─ 未触发 → 静默                                        │
│  └─ 触发 → 生成 RiskEvent                                │
│       ├─ 记录事件（rule_id, trigger_value, event_type）   │
│       ├─ 推送 WebSocket 实时消息                          │
│       └─ 按规则 action 执行：                             │
│           · alert → 仅推送通知                            │
│           · soft_block → 通知 + 拒绝新开仓订单              │
│           · hard_block → 通知 + 发起强制平仓               │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    告警层（事后前半段）                      │
│                                                         │
│  告警记录生成后进入处理队列：                                │
│  · 状态 = "处理中"                                        │
│  · 如果同一规则重复触发 → escalation_count 递增（x2, x3…）   │
│  · 严重级别 = critical 的告警优先处理                       │
│                                                         │
│  页面上的三张汇总卡提供快速入口：                             │
│  · "严重警报" → 点击直达告警列表 + 预筛选 critical 级别       │
│  · "活跃警报" → 点击直达告警列表 + 预筛选"处理中"状态          │
│  · "生效规则" → 点击切到规则配置页                           │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│                    处理层（事后后半段）                      │
│                                                         │
│  交易员/风控经理处理告警，三种结果：                         │
│                                                         │
│  1. 处理 → 弹出备注窗口，填写处理说明                       │
│     · 状态 → "已处理"                                     │
│     · 记录 resolved_by、resolved_at、resolution          │
│     · 示例："已止损减仓50%，剩余仓位跟踪止损"                │
│                                                         │
│  2. 忽略 → 直接标记                                       │
│     · 状态 → "已忽略"                                     │
│     · 适用于已知但无干预必要的场景                          │
│     · 示例："市场系统性风险导致，暂不干预"                   │
│                                                         │
│  3. 重新打开 → 已处理/已忽略的告警可重新激活                │
│     · 状态回到 → "处理中"                                 │
│     · 清除 resolved_by、resolved_at、resolution          │
│     · 场景：处理后被复核发现无效、或情况再次恶化             │
└─────────────────────────────────────────────────────────┘
```

# 回测验证业务流程：策略 → 配置 → 执行 → 分析 → 优化

整个流程分为**五阶段闭环**，由 BacktestEngine 驱动，通过事件系统对外广播进度。

## 页面职责划分

| 页面 | 路由 | 职责 | 定位 |
|:---|:---|:---|:---|
| **BacktestHub** | `/strategy/backtest` | 回测入口枢纽，汇总最近任务与快速入口 | 导航页 |
| **BacktestConfig** | `/backtest/config` | 单策略回测配置（策略选择、股票池、高级参数、风控约束） | 配置页 |
| **BacktestStudio** | `/backtest/studio` | 多策略对比回测 + 参数优化 | 工作室 |
| **BacktestReport** | `/backtest/report/:taskId` | 单次回测完整报告（净值曲线、交易明细、绩效指标、风险分析） | 报告页 |
| **BacktestPeriod** | `/research/backtest-period` | 预定义回溯周期管理 + 周期间对比分析 | 辅助工具 |

## 辅助工具：回溯周期（BacktestPeriod）

回溯周期是**预定义的时间区间模板**，用于在不同市场环境下批量验证策略鲁棒性。

```
策略 + 周期模板 → 批量回测 → 周期对比

示例：
  策略A ─┬─ 2023 牛市周期 → 年化 +23.5%，夏普 1.23
         ├─ 2022 熊市周期 → 年化 -12.3%，夏普 -0.45
         ├─ 2020 震荡周期 → 年化 +8.7%，夏普 0.67
         └─ 2018-2024 全周期 → 年化 +15.2%，夏普 1.10

对比结论：策略 A 在牛市中表现优异，熊市中回撤可控，整体鲁棒。
```

周期对比的指标维度：年化收益率、夏普比率、最大回撤、胜率。

## 回测工作室与回溯周期页面 — 符合性分析

### 回测工作室（BacktestStudio.vue）

| 维度 | 状态 | 说明 |
|:---|:---|:---|
| 策略选择 | ✅ 结构正确 | 穿梭框（Transfer）选策略，支持多选对比 |
| 回测参数 | ✅ 结构正确 | 日期范围、初始资金、基准指数 |
| 对比图表区 | ✅ 布局正确 | 净值曲线/绩效指标/回撤对比三 Tab |
| 参数优化区 | ✅ 布局正确 | ParameterOptimizer → HeatmapChart + ParameterTable |
| **API 集成** | ❌ 缺失 | `runMultiBacktest()` 直接赋值硬编码占位数据 |
| **实时进度** | ❌ 缺失 | 无 WebSocket 订阅回测进度事件 |
| **结果持久化** | ❌ 缺失 | 完成后未跳转报告页或持久化 |
| **exportResults** | ❌ 占位 | 显示"导出功能开发中" |
| **参数优化** | ❌ 占位 | `runOptimization()` 直接返回输入参数，未调用后端 |
| 状态覆盖 | ⚠️ 部分 | Loading/Error 已覆盖，缺少"运行中"进度态和 Empty 态 |

### 回溯周期（BacktestPeriod.vue）

| 维度 | 状态 | 说明 |
|:---|:---|:---|
| 周期 CRUD | ✅ 功能完整 | 新建/编辑/删除/搜索/筛选，表单验证齐全 |
| ECharts 图表 | ✅ 可视化完整 | 性能柱状图含年化收益+夏普+回撤三指标 |
| 周期对比 | ✅ 功能完整 | 多选周期 + 指标选择 + 柱状图对比 |
| 状态覆盖 | ✅ 完整 | Loading/Error/Empty/Data 四态 |
| **API 集成** | ❌ 缺失 | 周期数据存于本地 ref，未同步后端 DB（`backtest_scenarios` 表） |
| **回测触发** | ❌ 占位 | "回测"按钮仅显示提示，未跳转 BacktestConfig 或调用 API |
| **统计分析** | ❌ 硬编码 | `analysisStats` 为固定值，未根据实际数据计算 |
| **与工作室联动** | ❌ 缺失 | 选中周期后无法一键带入 BacktestStudio 进行批量回测 |

### 关键缺失与修复优先级

| 优先级 | 问题 | 影响 |
|:---|:---|:---|
| P0 | 三个回测页面均未接入后端 API | 回测结果非真实数据，无法验证策略有效性 |
| P1 | BacktestStudio 无进度跟踪 | 用户点击"多策略回测"后无反馈，体验中断 |
| P1 | 回溯周期"回测"按钮无效 | 功能入口存在但不可用 |
| P2 | 回溯周期统计为硬编码 | 新增/删除周期后统计数字不变 |
| P2 | 周期与工作室无联动 | 两页面功能割裂，无法形成闭环 |

### 建议修复路线

1. **BacktestConfig** 先接入后端 API（`create_backtest_task`），跑通单策略回测全链路
2. **BacktestStudio** 复用 BacktestConfig 的回测逻辑，扩展为多策略对比
3. **BacktestPeriod** 接入 `backtest_scenarios` 表，# 回测按钮跳转 BacktestStudio 并带入周期参数
4. 三个页面统一通过 WebSocket 订阅 `backtest.progress` 事件

# 数据同步业务流程：拉取 → 清洗 → 入库 → 缓存失效

数据同步是量化交易平台的**数据入口**，负责从外部数据源（Tushare Pro / Baostock）拉取 A 股全市场数据，
经清洗转换后写入 PostgreSQL（含 TimescaleDB 超表），并通过事件引擎向全平台广播同步进度。

## 同步数据类型（30+ 种，按业务域分组）

### 股票基础信息（4 种）

| 类型标识 | 目标表 | 同步方式 | 说明 |
|:---|:---|:---|:---|
| `STOCK_LIST` | `stock_basic` | 全量拉取 → 逐条 upsert | A 股全部上市股票基础信息（代码、名称、行业、上市日） |
| `COMPANY` | `stock_company` | 全量拉取 → 逐条 upsert | 上市公司基本信息（注册资本、员工数、主营业务） |
| `ST_LIST` | `st_list` | 日期范围拉取 → 逐条 upsert | ST/*ST 变更历史，仅保留 name 含 "ST" 的记录 |

## 同步模式：智能日期推断

`_resolve_sync_date_range(ts_code, start_date, end_date, repo)` 是决定同步策略的核心方法，根据数据库中已有数据自动判断四种模式：

```
                     ┌─────────────────┐
                     │  查询 DB 中该股票  │
                     │  最新交易日       │
                     └────────┬────────┘
                              │
              ┌───────────────┴───────────────┐
              │                               │
         无记录（首次同步）                 有记录
              │                               │
              ▼                               ▼
    ┌─────────────────┐             ┌─────────────────┐
    │  mode = "full"   │             │ start_date 是否  │
    │                  │             │ 由用户指定？     │
    │ start_date =     │             └────────┬────────┘
    │   上市日期 or     │                      │
    │   1990-12-19     │         ┌────────────┴────────────┐
    │                  │         │                         │
    │ 拉取全部历史数据   │     未指定                     已指定
    └─────────────────┘         │                         │
                                ▼                         ▼
                      ┌──────────────────┐    ┌──────────────────┐
                      │ latest + 1 天     │    │ mode = "overlap" │
                      │                  │    │                  │
                      │ > end_date ?     │    │ 按用户指定范围    │
                      │   YES →          │    │ 拉取（可能覆盖    │
                      │   "up_to_date"   │    │  已有数据）       │
                      │   NO →           │    └──────────────────┘
                      │   "incremental"  │
                      └──────────────────┘
```

| 模式 | 触发条件 | start_date | 行为 |
|:---|:---|:---|:---|
| **full** | DB 中无该股票任何记录 | 上市日期（回退到 1990-12-19） | 从上市日开始全量拉取 |
| **incremental** | DB 有记录 + 用户未指定起始日期 | 最后交易日 + 1 天 | 只拉取新增数据，高效增量 |
| **up_to_date** | 最后交易日 ≥ end_date | — | 跳过，无需同步 |
| **overlap** | 用户显式指定了 start_date | 用户指定的值 | 按用户范围拉取，可能覆盖已有数据 |

**设计优势**：
- 首次同步自动全量，后续自动增量，用户无需关心日期
- 单只股票级别的判断粒度，避免"一只新股导致全量重拉"
- 模式分布统计在同步结果 `mode_summary` 中返回，便于诊断

## 同步生命周期（6 步）

每次单类型同步遵循严格的 6 步生命周期，每一步均有事件广播和状态持久化：

```
API 请求 → sync_market_data(data_type, start_date, end_date, ts_codes)
  │
  ├─ 1. _create_sync_task()
  │     ├─ 生成 task_id（格式: sync_{data_type}_{YYYYMMDD_HHMMSS}）
  │     ├─ 估算 total_records（_estimate_total_items）
  │     ├─ INSERT data_sync_tasks（status="pending"）
  │     └─ 写入缓存（TTL 24h，供前端轮询）
  │
  ├─ 2. _publish_sync_event("started")
  │     └─ DataSyncStartedEvent → EventEngine → WebSocket 推送前端
  │
  ├─ 3. _sync_by_data_type() → _sync_method_map[data_type]()
  │     ├─ DataSourceFactory.get_source("tushare")  → 数据源适配器
  │     ├─ _run_in_executor(source.get_xxx)          → 线程池隔离同步 IO
  │     ├─ _convert_records_datetime()               → pandas Timestamp → Python datetime
  │     ├─ _clean_nan_values()                        → NaN → None（兼容 asyncpg）
  │     ├─ Repository.create/update                   → PostgreSQL 持久化
  │     ├─ _update_progress()                         → 缓存（节流：≤1次/秒）
  │     └─ session.commit()                           → 每 N 只提交一次
  │
  ├─ 4. 判断最终状态
  │     ├─ records_added + records_updated == 0 且 total > 0 → status="failed"
  │     │   错误信息: "全部 N 条记录同步失败，无成功记录"
  │     └─ 至少有一条成功 → status="completed"
  │
  ├─ 5. _publish_sync_event("completed" / "failed")
  │     └─ 成功时清理缓存，失败时保留旧缓存
  │
  └─ 6. _clean_cache_after_sync()（仅成功时）
        └─ 按 pattern 删除 Redis/内存缓存中的过期数据
```

## 逐股同步通用模式

大部分行情和财务数据采用**逐股同步**模式，以 `_sync_daily_quotes` 为参考模板：

```
for idx, ts_code in enumerate(ts_codes):     # ~5000-5500 只股票
  │
  ├─ _is_cancelled()? → break                 # 双重取消检查（token + DB）
  │
  ├─ _resolve_sync_date_range(ts_code, ...)   # 智能判断 full/incremental/up_to_date
  │   └─ mode == "up_to_date"? → records_skipped++, continue
  │
  ├─ source.get_daily(ts_code, s_date, e_date) # Tushare API 调用（线程池执行）
  │
  ├─ _convert_records_datetime() + _clean_nan_values()  # 数据清洗
  │
  ├─ _process_trade_date_data(repo, data, ts_code)      # 逐条 upsert
  │   ├─ 按 trade_date 查重
  │   ├─ 已存在 → update_by / update(id)    → records_updated++
  │   └─ 不存在 → create                    → records_added++
  │
  ├─ 每 10 只 commit + 进度日志               # 减少事务锁竞争
  │   logger.info(f"[日行情] {idx+1}/{len} ({pct}%) 新增={added} 更新={updated}")
  │
  └─ _update_progress(task_id, progress, ...)  # 写入缓存（节流 ≤1次/秒）
```

**性能估算**（Tushare 免费版限速下）：
- 日行情全量（5000 只 × 250 天）：约 25 分钟
- 日行情增量（最新 1 天）：约 3-5 分钟
- 财务指标全量（5000 只 × 20 条/只）：约 20-30 分钟
- ETF 日线全量（1000 只）：约 5 分钟

## 批量同步

### 串行模式 (`batch_sync`)

```
for task_item in request.tasks:
    sync_market_data(data_type=task.data_type, ...)  # 等待完成再执行下一个
```

- 共享同一个 session，适合少量、有依赖关系的同步
- 发布 `batch_started` / `batch_completed` / `batch_failed` 事件

### 并行模式 (`batch_sync_data`)

```
asyncio.Semaphore(3)  # 最多 3 种类型并行

for task in tasks:
    _sync_one(task):                          # asyncio.gather 并发
        session = get_new_session()           # 独立 session（隔离事务）
        svc = DataSyncService(session, ...)   # 独立实例
        svc.sync_market_data(...)
```

- 每种类型独立 session + 独立 `DataSyncService` 实例
- `asyncio.Semaphore(3)` 限制并行度，避免 Tushare 限流
- 子任务传 `update_task_status=False`，**不更新批量任务状态**；全部完成后由 `batch_sync_data` 统一写 DB + 聚合记录数
- 日志标签统一为 `[batch:中文(英文)]` 格式，`grep '\[batch'` 可过滤全部批量日志
- 墙钟时间 ≈ 最慢类型的时间（而非累加）

## 取消机制

取消采用**双重保障**设计，确保取消失败时也有兜底：

```
cancel API (/sync/cancel)
  │
  ├─ 1. signal_cancel(task_id)          ← 第一层：设置 asyncio.Event（内存信号）
  │     └─ _cancel_tokens[task_id].set()
  │
  └─ 2. UPDATE data_sync_tasks          ← 第二层：DB 状态（持久化标记）
        SET status = 'cancelled'

同步循环中的检查（_is_cancelled）：
  │
  ├─ 第一层：self.cancel_token.is_set()?   ← O(1) 内存读取，每只股票检查一次
  │   └─ YES → 立即 break
  │
  └─ 第二层（回退）：DB 查询 status       ← token 失效时兜底
      └─ status == 'cancelled'? → break
```

**关键设计决策**：
- `signal_cancel()` 在 handler 中**优先于 DB 操作**执行（确保即使后续 DB 操作失败，token 也已设置）
- `_is_cancelled()` 在 token 未命中时回退到 DB 查询（兜底）
- `task_id` 通过 `DataSyncService.__init__(task_id=...)` 传递链注入

```
  │
  └─ 回退：Baostock（免费，无需 token，但数据覆盖面和时效性不如 Tushare）
      ├─ 股票：query_stock_basic, query_history_k_data_plus ...

```

### 取消流程（简化后）

```
Handler.cancel_sync(task_id):
  ① DB: UPDATE status='cancelled', commit
  ② signal_cancel(task_id)         → 设置 asyncio.Event（微秒级）
  ③ return                         → 毫秒级响应

Worker 检测到 _is_cancelled() → 提前返回
_parallel_for_each 返回 {cancelled:True}
sync_market_data → _update_sync_task("cancelled") + commit
_execute_sync_task → 引擎内存状态 = CANCELLED
```

三层防覆盖机制：
- `_update_sync_task`：终态（completed/cancelled）不被非 cancelled 覆盖
- `_execute_async_data_sync`：写 `running` 前先查 `cancel_token.is_set()`
- `_execute_sync_task` 结束后用 `cancel_token.is_set()` 不用 DB 缓存判断取消

## 错误处理策略

| 场景 | 处理方式 | 影响范围 |
|:---|:---|:---|
| **单只股票 API 调用失败** | 记录 error 日志 + `records_failed++`，继续下一只 | 仅该股票 |
| **单条记录写入失败（非唯一键冲突）** | 记录 warning 日志 + `records_failed++` | 仅该条记录 |
| **唯一键冲突 → update 也失败** | 记录 warning（含具体异常） + `records_failed++` | 仅该条记录 |
| **唯一键冲突 → update 成功** | `records_updated++`（算成功） | — |
| **全部记录失败** | status → "failed"，发布 failed 事件 | 整个任务 |
| **NaN 值** | `_clean_nan_values()` 转为 None | 所有记录自动处理 |
| **Tushare 多余字段** | 按 ORM 模型列名过滤（`known_cols`） | 所有记录自动处理 |

# 写入层架构（2026-06-04 重构）

## Facade 模式：`_process_trade_date_data`

所有行情类同步方法（9 个）统一通过 `_process_trade_date_data` Facade 写入，调用方无需判断模式：

```python
# 所有调用方统一为一行
added, updated = await self._process_trade_date_data(repo, data, ts_code)
records_added += added; records_updated += updated
```

Facade 内部自动选择最优路径：

```
_process_trade_date_data(repo, data, ts_code)
    │
    ├─ try: repo.bulk_upsert(data)        ← 批量 ON CONFLICT DO UPDATE
    │     成功 → return (count, 0)
    │
    └─ except: 回退逐条 upsert             ← 表无 UNIQUE 约束时自动兜底
         for item in data:
             get_by_trade_date → create / update_by
```

## `bulk_upsert` vs `batch_upsert`

`BaseRepository` 提供两个 upsert 方法，职责不同：

| 方法 | 签名 | 冲突键 | 场景 |
|------|------|------|------|
| `bulk_upsert(records)` | 1 参数 | **自动推断**（UniqueConstraint → PK → 业务键 fallback） | 数据同步 |
| `batch_upsert(match_fields, data_list, update_fields)` | 3 参数 | 调用方**显式指定** | 业务写入 |

`bulk_upsert` 冲突键自动检测优先级：

```
1. __table_args__ 中的 UniqueConstraint     → 最精确（如 stock_daily 的 (ts_code, trade_date)）
2. 非 id 的 PrimaryKey                      → index_daily 的 (ts_code, trade_date)
3. 常见业务键 fallback                       → ['ts_code','trade_date'] / ['ts_code','end_date'] / ['ts_code']
```

特性：
- 分页 1000 条/批，防 PostgreSQL 32767 参数上限
- 异常时 `await session.rollback()` 后 re-raise，避免事务中止影响后续查询
- `IndexDailyRepository` 独立实现 `batch_insert`（`ON CONFLICT DO NOTHING`），用于分钟数据场景

## `_preprocess_records` — 数据预处理合并

将原来分散的 3-5 趟循环合并为 1 趟：

```python
def _preprocess_records(records, date_fields=(), known_cols=None):
    """
    一趟完成：pandas 类型转换 + NaN 清洗 + 日期字符串转换 + 多余列过滤。
    替代 _convert_records_datetime + _clean_nan_values + for item in data 循环。
    """
    for record in records:
        # pandas Timestamp → datetime，NaN → None
        for key, value in list(record.items()):
            if isinstance(value, pd.Timestamp): record[key] = value.to_pydatetime()
            elif isinstance(value, float) and math.isnan(value): record[key] = None
            elif hasattr(pd, 'isna') and pd.isna(value): record[key] = None
        # 日期字符串 → date
        for field in date_fields:
            if record.get(field): record[field] = _convert_to_date(record[field])
        # 过滤多余列
        if known_cols:
            for key in list(record.keys()):
                if key not in known_cols: del record[key]
    return records
```

已应用：15 个方法（所有 `for item in data` + `_clean_nan_values` + 日期转换 的循环全部替换）
未应用：`_sync_financial_statement`（使用 `_convert_to_datetime`，需加 `datetime_fields` 参数）

## 取消机制增强：`_is_cancelled`

双重检查，DB 结果缓存：

```
_is_cancelled()
    │
    ├─ self.cancel_token.is_set()?          ← O(1) token 检查（每次循环）
    │   └─ YES → return True
    │
    └─ 首次调用时查 DB status='cancelled'?   ← 仅一次，结果缓存为 self._db_cancel_checked
        └─ YES → 同步设置 token + return True
```

`task_id` 通过 `DataSyncService.__init__(task_id=...)` → `batch_sync_data` 子实例全程传递。

## 状态判定修复

`sync_market_data` 根据实际结果判定最终状态：

| 条件 | 状态 |
|------|------|
| `added + updated == 0` 且 `total > 0` | `failed`（全部失败） |
| 至少一条成功 | `completed` |
| cancel_token 已设置 | `cancelled` |

`_execute_async_data_sync` handler 同步检查 `sync_result["success"]` 后再写 `status`。
