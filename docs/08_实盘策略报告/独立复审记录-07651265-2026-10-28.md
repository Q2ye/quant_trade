## 三、复审报告原文

策略审查报告：跨市场动量避险轮动-实盘-2.0（07651265）

### 阻断级问题

无。未发现会导致「直接亏钱/错误成交且无人工拦截」的确定性缺陷。sizing 不封顶、T+1 语义不完备、退出重发 churn 三处均为**已在代码注释中明示的有意偏离**，且半自动模式下人工/券商是最后一道拦截。它们达到高危，但不到阻断。

### 高危问题

#### H1. `fill_date` 只在「当日确认成交」当天存在 → T+1 守卫形同「仅保护成交确认当天」

`_live_code_07651265.py:1992`（`fill_date=td`）是**唯一**写入 `fill_date` 的位置；`_normalize_holdings`（`:2005-2013` 注释）与框架 `_restore_positions_from_db`（`strategy_manager.py:2211-2216`）都**刻意不补** `fill_date`。而框架每日驱动前都会 `_restore_positions_from_db` 清空 `_holdings` 并从 `positions` 表重建，重建字典只含 `{entry_price, weight, shares, locked}`。

- 「补 fill_date → 永久冻结」的方向**已被正确规避**：`_normalize_holdings` 不补 `fill_date`，故 `fill_date == td` 不会每天都成立，不存在冻结。✅
- 但相反方向**存在**：一个持仓只要**不是**在「pending 买单 → 当日 DB 出现该持仓」这条路径上进入 `_holdings`，就**永远没有 `fill_date`**，T+1 守卫（`:888`、`:1746`）对它永远不生效。具体链路：信号日 T 发出买单 → T+1 人工未成交 → `_move_pending_to_holdings` 丢弃该 pending（`:1973-1980`，代码不在 `_active_positions`）并 `clear()` → T+2 人工才成交并录入 DB → T+2 驱动重建 `_holdings[X]`（无 `fill_date`）→ `_normalize_holdings` B4 兜底把 `_held_days[X]=min_hold_days`（`:2028-2029`）→ 若 X 已不在目标池，`_should_retry_exit` 首日即 True（不在 `_exit_pending`）→ **成交当日就发出卖出信号**。真·T+1 违规由券商结算拦截，但信号语义上是「当日买入当日卖」。这是注释 `:2011-2013` 承认的「恢复当日可卖」代价，在**延迟成交**这一已发生事件（人工延迟 1 日）下会被实际触发。

> **2026-10-28 裁决：接受** —— 券商 T+1 结算兜底；实际代价是信号语义与一次进出成本，由人工核单控制。

#### H2. 退出重发 + F4 交互：已登记退出的标的重新入选目标后仍被强制卖出，且 reason 文案撒谎

卖出循环 `:885-898`：`if code in target_codes and code not in self._exit_pending: continue` 意味着**只要在 `_exit_pending` 里，即使今日在目标池也不保留**（F4 有意设计）；随后 `:893` 的 `_should_retry_exit` 在 `exit_retry_days`（3 个调仓日）后放行重发，`:896` 的 reason 固定写 `"轮动换仓: 不在目标池"`。

**触发条件 + 失败场景**：标的 X 跌出目标池（登记退出 `_exit_pending[X]`）→ 3 日内动量恢复、重新入选目标池，且人工未执行最初的卖单 → 第 3 个调仓日 `_should_retry_exit` 返回 True → 对**当前就在目标池里的 X** 再次发出卖出信号，reason 仍写「不在目标池」（事实错误）。次日卖出成交 → `_reconcile_holdings` 摘除 `_exit_pending[X]`/`_holdings[X]` → 之后该标的若仍在目标池会被重新买入。净效果：F4 想避免的「卖出→摘除→买回」churn 被重发机制重新引入，且框架只对买单做去重/取消（`_check_yesterday_pending` 只查 `pending_manual` 买单，`strategy_manager.py:2441-2452`），卖单不去重 → 同一标的可能同时挂两张 pending 卖单。

> **主会话订正**：「同日买入循环立刻又买回」不成立 —— 买入循环 `:907` 会跳过 `code in self._exit_pending`，买回只能发生在后续交易日对账摘除之后（详见 §四）。

#### H3. sizing 不封顶可用现金：`total_assets × weight`（≤90%），忽略 `available_capital`

`resolve_sizing_capital()` 返回 `context.total_assets`（`base_strategy.py:449-457`），`calculate_position_size`（`:1950-1954`）与 `_make_entry_signal`（`:1777-1784` 注释明示「有意偏离资金契约 §2.1」）都**不调用** `resolve_available_cash()`。实盘 `context.total_assets` 每日同步为账户 `total_balance`，`context.available_capital` 同步为 `available_balance`。

**触发条件 + 失败场景**：卖出未成交/延迟成交时 —— T 日同时发「卖 X + 买 Y」（`order_mode=open`）。若人工只执行了买 Y 未执行卖 X（或卖被拒），买单金额按 `total_assets × weight ≈ 权益的 90%` 计算，而可用现金只剩约 10% → **发出超出可用现金的买单**。半自动下人工会被券商拒单或部分成交；`risk_budget_pct`/`qty_at_limit`（`:1819-1829`）提供了人工缩量依据，但**代码层没有任何「买单金额 ≤ 可用现金」的闸门**，也不存在「卖不掉→就不买」的资金死锁保护（唯一的保护是 `has_t1_locked_sell`，它只覆盖「今日刚成交的持仓待卖」，不覆盖「昨日成交、今日待卖、人工未执行」）。

> **2026-10-28 裁决：接受 + 人工控制** —— 同日出现「卖 X + 买 Y」时，**人工必须先执行卖出、再执行买入**；若卖单未成交，不得先买 Y。

#### H4. `min_hold_days` 早退分支无日志，且不豁免「走弱期已进入」的换仓

`:844-847`：`if (min_hold_days > 0 and self._holdings and not signals and self._index_cache_ok): if all(held_days < min_hold_days): return signals` —— **直接 `return`，零日志**。注释 `:840-843` 只豁免降级日（`_index_cache_ok is False`），**没有**豁免「regime 刚翻入走弱期」这一更高优先级的换仓信号。

**触发条件 + 失败场景**：持仓是 A 股 ETF、持有未满 3 个交易日时，4 指数 MA10 投票翻入走弱期 → 本应立刻切全球/防御池，但被 `min_hold_days` 守卫**静默拦下**，最多在 A 股 ETF 里多待 2 个交易日，且当日 `get_target_pool` 返回 None（`:2165` 起，早退分支），诊断层也看不到「今天本来要换仓」。与策略「A股走弱即避险」的第一性原理直接冲突，且无任何日志可追溯。

### 建议改进

#### S1. `_update_weak_period` 与 `_compute_weak_streak` 对「非法指数价格」的投票口径不一致

`_update_weak_period`（`:941-952`）直接 `np.mean(recent)`、`current > ma / current < ma`，**不检查 NaN/≤0**；`_compute_weak_streak`（`:1042-1043`）则 `np.all(np.isfinite(window)) and not any(window<=0)` 才投票。若 `index_daily.close` 出现 0.0 或负值，实际 regime 状态机会把 0 价计为「below」（看跌票），而监控口径 `_weak_streak` 会跳过该日 → **诊断显示的连续走弱天数与实际交易状态分叉**。当前数据下未命中，属低概率数据质量边界。

#### S2. `_make_exit_signal` 的「以 broker 实际持仓数量为准」在实盘是死代码

`:1839-1847`：`bp = self.context.positions`，实盘路径 `context.positions` 恒为空 dict（`_reconcile_holdings` docstring `:2033-2037` 明示「实盘从不写该字段」），故 `if bp:` 恒 False，卖出数量回落到策略自维护的 `_holdings[code]["shares"]`。

> **主会话订正**：该 `shares` 在实盘**通常是 DB 真数**（`_restore_positions_from_db` 每日用 `positions.volume` 重建 `_holdings`，`strategy_manager.py:2208-2215`），偏差窗口仅限「成交当日」这一日，而非长期使用信号数量。但「`context.positions` 在实盘恒空 → broker 覆盖分支是死代码」这一结论成立。

#### S3. `_held_days` 无清理对称性，跨持仓生命周期可能残留

`_restore_positions_from_db` 只清 `_holdings` 不清 `_held_days`；`_held_days` 仅在 `_reconcile_holdings` 的幽灵删除分支被 pop。若某持仓经「卖光→框架 DB 删除」路径离开而 `_reconcile_holdings` 恰在 fail-open 分支（`:2051-2053`）返回，`_held_days` 会残留过期键，影响后续 `all(held_days < min_hold_days)` 的判定基数。低概率、仅内存，不影响 DB。

> **主会话实测佐证**：`strategy_runs.state_snapshot` 中仍见 `_held_days` 残留 `159985.SZ: 14`、`513100.SH: 15`（两只均已清仓），确认该现象存在。

### 无法验证项

1. **`strategy_parameters` 表覆盖 vs `DEFAULT_PARAMS`**：本文件只是 `strategies.code` 导出，运行时参数 = `DEFAULT_PARAMS` + `strategy_parameters` 覆盖（`__init__` `:420-422`）。有效开关（`enable_trend_quality=True` / `enable_rel_strength=True` / `enable_entry_gain_filter=False` / `momentum_efficacy_threshold=-1.0` / `vol_target_annual=0.0`）是否与 DB 覆盖一致，只能查 `strategy_parameters` 表，无法从本文件判。
2. **NAV 漂移 / 前复权一致性 / equity_curve 误差 <1e-8**：发生在框架撮合与账户结算层，策略文件只消费 `BarData`，本文件内无对应计算可审。
3. **`_momentum_efficacy` 的安慰剂 lag、vol_targeting、risk_adj 三套「仅回测验证」参数**：默认全关，其正确性只能靠回测 harness 验证，本文件无法静态确认。
4. **「10-23 日志说不重复登记、DB 却新增买单」的修复是否彻底**：输出层抑制现已在 `_publish_signals` 之前执行（`strategy_manager.py:778-786`，**工作区未提交**），但当前框架是否还有其它落库路径绕过此抑制，需在 `signal_engine` / `_persist_signal` 侧复核（不在本次审查对象内）。
