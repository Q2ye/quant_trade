# Review 报告校准说明（基于真实业务模式二次核实）

> 2026-08 | 目的：以两个业务前提为准，重新核实 review 报告结论的准确性，避免"按错误假设修复引入更多问题"。
>
> **前提 1（业务模式）**：半自动交易——系统生成信号 → 人工在券商交易 → **手动录入订单（POST /trades/record）** → 系统读取订单。主链路是**录单链路**，不是 ExecutionEngine 自动成交链路。
> **前提 2（系统定位）**：资金快速膨胀期——风控从宽、追求最大收益。

---

## 一、真实主链路实证（代码核实结果）

`api/routers/trade_router.py:475` `POST /trades/record`（docstring 明确"用户在券商端手动完成交易后，回到系统记录成交信息"）
→ `handlers.record_trade`（:511）
→ `TradeRecordService.record_filled_trade`（`trade_record_service.py:89-237`），**单事务内 7 步完整闭环**：

| 步骤 | 实现 | 校验 |
|:---|:---|:---|
| 1 账户 | `get_many_by_user_id` | ✅ 无账户报错 |
| 2 费用 | 用户填写或统一费率计算 | ✅ |
| 3 订单 | Order status=filled（order_id 关联 signal_id/strategy_id） | ✅ |
| 4 成交 | Trade + filled_at=trade_date | ✅ |
| 5 费用明细 | TradeFee 多条 | ✅ |
| 6 持仓 | `_upsert_position`（:276-362） | ✅ **卖出无持仓拒绝（:299-302）、超持仓拒绝（:336-339）**、加权平均成本、按 (account, ts_code, strategy) 隔离 |
| 7 账户 | `_update_account_balance`（:364-405） | ✅ 现金↔持仓转换、总资产只随费用减少（修复过） |
| 8 信号回写 | `signal_id` → `signal_status="executed"` + order_id（:223-227） | ✅ 信号→成交闭环**在录单链路是通的** |

**信号审核链路**：`review_signal`（handlers.py:610-652）：`pending_manual → approved/rejected`，防重（非 pending 状态拒绝重复审核）+ reviewed_by 审计。approved = **"已采纳待成交"**，成交闭环由录单携带 signal_id 完成。

## 四、结论

1. **review 报告的主体结论仍然准确**：数据层（03）、共享层（02）、安全（06/07）、回测（04）、前端（08）、引擎基座（01）的发现与交易模式无关，全部成立。
2. **05 报告的交易链路结论需要按"录单为主链路"重评**：9 项 P0 中，4 项降级为"自动模式预备"（P2），2 项修正定性（approved 闭环不成立、风控宽松是设计意图），3 项维持/调整（pnl 回填缺口、信号确认无认证、SIMULATED_TRADING 防御）。
3. **录单主链路本身经核实是健康正确的**（7 步事务闭环 + 持仓/资金校验 + 信号回写），这解释并验证了当前系统半自动运行可行的原因。
4. 按上述校准执行修复，**不会**"把好链路修坏"——原批次 2 的自动链路问题整体移到"自动模式预备"批次，当前不动。
