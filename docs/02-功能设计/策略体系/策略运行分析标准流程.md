# 策略运行分析标准流程（实盘 / 日终）

> **适用范围：所有策略的实盘/日终运行分析**（每日 EOD 流水线、状态机健康、执行确认、异常检测）。
> 与《回测分析标准流程.md》互补：回测回答"策略好不好"，运行分析回答"今天策略有没有按设计正常跑、要不要干预"。
> 铁律：**运行分析的目的不是评价收益，而是确认状态机健康 + 发现需人工干预的异常。**

---

## 〇、流程总览

```
Step 1  数据完整性 ────── 日终同步/覆盖校验是否通过（数据是策略的地基）
   ↓
Step 2  市场状态 ──────── regime 判定 / 宽度 / 指数（策略门控依据）
   ↓
Step 3  资金与账户 ────── 资金分配 / 组合 rebalance / 账户结算
   ↓
Step 4  策略状态机 ────── 每个运行中策略：信号 / 持仓 / 候选 / 诊断计数
   ↓
Step 5  执行确认 ──────── 买入确认（跳空/破位）、量能确认、信号价 vs 收盘价
   ↓
Step 6  异常与健康度 ──── 幽灵持仓 / 拦截 / 漂移 / 计数异常
   ↓
Step 7  结论 ──────────── 正常 / 需关注 / 需干预
```

---

## 一、Step 1：数据完整性（地基）

**证据**：日志中 `日终同步` / `覆盖度校验` / `数据完整性校验` / `market_state` 行。

| 检查项 | 正常 | 异常 |
|:---|:---|:---|
| 日终同步各类型 | 完成（records 可 0，若当日无新数据属正常） | 出现 `failed` / 卡 `running` |
| **覆盖度校验** | `覆盖正常` | `N 只股票覆盖不足` → 需回填（`scripts/data/backfill_coverage_gaps.py`） |
| **数据完整性门** | `通过: stock_daily 最新=当日, N 条`（N≥4000） | 未通过 → 跳过策略驱动（防旧数据假信号） |
| market_state 写入 | `5196 条` 等 | 写入失败 |

**判定**：任一数据门失败 → **当日策略驱动被跳过或结果不可信**，先修数据。

---

## 二、Step 2：市场状态

**证据**：`market_state_classifier` / `CapitalAllocator rebalance` 的 `regime`。

| 检查项 | 说明 |
|:---|:---|
| regime 判定 | 0=熊 / 1=震荡 / 2=牛（CapitalAllocator 依据） |
| 资金分配 | `alloc={'attack': x, 'defense': y}` 是否与 regime 匹配（牛攻高/熊守高） |

**判定**：regime 是否合理（对照当日市场）；分配比例是否符合组合配置预期。

---

## 三、Step 3：资金与账户

**证据**：`CapitalAllocator rebalance` / `组合每日 rebalance` / `日终结算`。

| 检查项 | 说明 |
|:---|:---|
| 组合 rebalance | 总资金 / 各策略运行资本（`运行资本`）是否合理 |
| 账户结算 | 每个账户结算完成；`当日盈亏` 是否异常大（需排查） |

**判定**：资金分配到位、结算无异常。

---

## 四、Step 4：策略状态机（每个运行中策略）

**证据**：每个策略的 `load_live_state` / `调仓` / `选股` / `候选入池` / `[策略诊断]` 行。

| 检查项 | 说明 |
|:---|:---|
| 重启恢复 | `恢复持仓 N 只` / `恢复候选 N 只` 是否与预期一致 |
| 状态机阶段 | 调仓/门控/选股是否按设计推进 |
| 选股结果 | Top N 及评分是否符合策略逻辑 |
| **诊断计数** | `[策略诊断]` 的各类计数是否偏离常态（如 `entry_generated` 长期 0、`warmup_skip` 占比异常） |

**判定**：状态机推进正常、计数在合理范围。**计数长期偏离 = 策略漂移**（需定位）。

---

## 五、Step 5：执行确认

**证据**：`买入确认失败` / `量能确认拦截` / `跳空` / `破位` 等执行层日志。

| 检查项 | 正常 | 需关注 |
|:---|:---|:---|
| 买入确认（收盘 vs 信号价） | 确认通过 → 入池 | `收盘 ≤ 信号价`（跳空低开）→ 放弃买入（执行纪律） |
| 量能确认 | vol_ratio ≥ 阈值 | `vol_ratio<1.0` → 拦截（量能不足） |
| 破位/跳空拦截 | — | 出现即放弃（防追高/破位） |

**判定**：执行纪律是否正确拦截（拦截≠故障，是风控在起作用）；确认失败频率是否异常（频繁失败 = 信号价/触发逻辑问题）。

---

## 六、Step 6：异常与健康度

**证据**：`幽灵持仓` / `无持仓可卖` / 各类 `拦截` / 覆盖度。

| 异常 | 严重度 | 处理 |
|:---|:---|:---|
| 幽灵持仓（策略状态 vs 实际持仓不一致） | 🔴 | 清理 + 排查状态重建逻辑 |
| 无持仓可卖（卖出作废） | 🟠 | 状态 desync，需排查 |
| 量能/跳空拦截频率异常 | 🟠 | 触发或执行参数问题 |
| 覆盖度不足 / 数据门失败 | 🔴 | 先修数据 |

**判定**：无 🔴 异常 = 健康；有 🟠 = 记录并观察；🔴 或连续 🟠 = 需人工干预。

---

## 七、Step 7：结论

| 结论 | 含义 | 动作 |
|:---|:---|:---|
| ✅ 正常 | 数据完整、状态机健康、执行纪律正常 | 无需动作 |
| ⚠️ 需关注 | 有 🟠 级现象（单次拦截/小异常） | 记录观察，次日复查 |
| 🔴 需干预 | 数据门失败 / 幽灵持仓 / 连续异常 | 修数据 / 清理状态 / 定位根因 |
