## 二、根因（代码级，已定位到行）

```python
# shared/sources/tushare_source.py:156 —— 数据源【本身支持】L/D/P
def get_stock_basic(self, exchange: str = '', list_status: str = 'L') -> List[Dict]:
    ...
    df = self.pro.stock_basic(exchange=exchange, list_status=list_status, fields=fields)
                                                        ↑ 支持 L-上市 / D-退市 / P-暂停上市

# modules/data/services/sync_service.py:2067 —— 调用方【从不传参】
stock_list = await self._cancellable_run_in_executor(source.get_stock_basic, )
                                                                     ↑ 空 → 走默认 'L'
```

**→ 永远只拉 `L`，`D`/`P` 从未被拉取过。**

> ⚠️ 这不是孤例：`baostock_source.py:102`、`mock_source.py:107`、`base_source.py:37`
> 的 `get_stock_basic` **默认值同样是 `'L'`** —— 抽象层的默认值设计使这个漏传"静默发生"。

## 四、⚠️ 附带发现：`L` 列表本身也不一致

对比 Tushare 的 `L` 与 DB 的 `stock_basic`：

```
DB 5531 只 / Tushare(L) 5565 只
  Tushare(L) 有而 DB 无 :  48 只   ← 当前上市的股票，DB 缺 48 只
  DB 有而 Tushare(L) 无 :  14 只   ← DB 标 L，但已不在 L 列表
```

**含义**：**问题不止"退市股没同步"，而是"同步本身有遗漏与滞后"。**

- 48 只缺失 → 可能是同步后新上市未及时补，或同步遗漏
- 14 只多余 → 可能已退市/暂停但 DB 状态未更新

**建议单独核查**（本次不做结论）。

## 五、修复与回填记录（**已实施** 2026-09-19）

### 5.1 代码修复（3 处）

| # | 文件 | 改动 |
|:--|:---|:---|
| 1 | `modules/data/services/sync_service.py:2067` | 调用改为**遍历 `('L','D','P')` 三次拉取并合并**，并逐次记录条数 |
| 2 | `shared/sources/tushare_source.py:156` | 默认值 `'L'` → **`''`（空=全部）**；空值时展开为 L/D/P 三次拉取。**并强制给每条记录打 `list_status`**（见 5.2 陷阱） |
| 3 | `shared/sources/{base,baostock,mock,xtp}_source.py` | 默认值同步改为 `''`，docstring 注明语义；标注"本实现不使用该参数"者 |

> **为何把默认值改成「空=全部」而非「强制显式传参」**：
> 后者会破坏 3 处现有调用（`mock` 内部 + 2 个测试），且只是编译期约束；
> 前者让**漏传时 fail-safe 拿全部**，方向正确且零破坏。

### 5.2 ⚠️ 修复过程中发现的两个陷阱（都已处理）

**陷阱 A —— `list_status` 会丢失，退市股被写成"上市股"**

```python
fields = ('ts_code,symbol,name,area,industry,market,exchange,list_date,delist_date,is_hs')
                                                                              # ↑ 不含 list_status
```
而 DB 列 `stock_basic.list_status` 的默认值是 **`'L'`** →
**合并 L/D/P 时若不显式打标，339 只退市股会全部写成 `'L'`** ——
**比不补还糟**（它们会被当成正常标的参与选股）。
→ 已在源实现中强制 `_df["list_status"] = _st`。

**陷阱 B —— 部分退市股的 `market` 为 NULL，而该列 NOT NULL**

```
T600018.SH 上港集箱(退)   → market=None
→ NotNullViolationError: null value in column "market"
```
`stock_basic` 的 NOT NULL 列：`ts_code / symbol / name / market / list_date`。
→ 已按**代码段推断板块**（代码段是板块的权威来源）。

**陷阱 C（非本次引入，但本次暴露）—— 14 只标的「状态过期」**

```
000004.SZ 国华退  → DB 中 list_status='L'、delist_date=NULL，而 Tushare 记为已退市(2026-07-14)
```
即前面 §四「DB 有而 Tushare(L) 无 : 14 只」的那批。
→ `stock_basic` 的冲突策略改为
**`DO UPDATE SET list_status, delist_date`（只覆盖状态字段，不动 area/industry/name）**，
而非 `DO NOTHING`——否则改不动它们。
