# 数据清洗现状 · 核查记录（2026-09-19）

> **触发**：核查「清洗是否在同步后执行」「是否所有类型都清洗」。
> **方法**：全仓静态扫描 `modules/data/services/sync_service.py`（59 个 `_sync_*`）+ 调用点追踪。
> **结论**：**没有"同步后清洗"环节**；**所谓"清洗"实质是"入库前类型适配"**；
> 真正的质量清洗**代码已写但从未接线**。

---

## 一、三层名为"清洗"的东西，只有第一层在跑

| # | 形式 | 位置 | 是否执行 | 性质 |
|:--|:---|:---|:---|:---|
| **1** | `_convert_records_datetime`（→ `_clean_nan_values`）<br>`_preprocess_records`（**内联** NaN 清理） | `sync_service.py:292 / :434` | ✅ **同步写入前** | **类型适配**（让数据能进 asyncpg） |
| **2** | `clean_invalid_data`（去重 / 修缺失） | `quality_service.py:707` | ❌ **从不被调用** | **质量清洗** |
| **3** | `DataClean*` 事件族（6 个） | `events/clean_events.py` | ❌ **从不发布/订阅** | **事件驱动清洗管线**（死代码） |

> 另：`_clean_cache_after_sync`（`sync_service.py:5960`）清的是**缓存**，不是数据，不属此列。

### 1.1 第 1 层的实质是「适配」而非「清洗」

`_preprocess_records` 的 docstring 自述：

> **"一趟完成：pandas类型转换 + NaN清洗 + 日期转换 + null→0填充 + 列过滤。"**

`_clean_nan_values` 做的是 **`NaN → None`** —— 这是**为了兼容 asyncpg**
（pandas 的 `NaN` 是 float，写不进 `numeric`/`varchar` 列）。

**→ 即：本项目的"清洗"实质是「让数据能入库」，不是「让数据变干净」。**

### 1.2 第 2 层为何从不执行（代码观察，未验证）

- `clean_invalid_data` 是 `@staticmethod`，签名 `(data, data_type, cleaning_rules)` ——
  **需要调用方传清洗规则，而没有任何"默认规则来源"**
- `DataClean*` 事件族很完整（`Started` / `Progress` / `Completed` / `Failed` / `Applied`），
  **像是设计了一条事件驱动清洗管线，但从未有生产者**

两层看起来是**不同时期分别设计**、均未接线。

## 四、⚠️ 本次排查中我自己的三次判断失误（记录为教训）

排查过程中我连续三次基于**不完整的扫描**下结论，每次都被更深的检查推翻：

| 次 | 我的判断 | 错在哪 | 真相 |
|:--|:---|:---|:---|
| 1 | `clean_invalid_data` 无调用点 → "没有清洗" | 只查了一个函数名 | 同步链路里另有 `_preprocess_records` 路径 |
| 2 | "22 个 `_sync_*` 未走 `_preprocess_records` → 未清洗" | **只查了两个函数中的一个** | 那 22 个多数用 `_convert_records_datetime` |
| 3 | "`_preprocess_records` 不调 `_clean_nan_values` → 它不清洗" | **只看调用、没读实现** | 它**内联**做了同样的 NaN 清理（docstring 明写） |

**共同错误模式**：**用"符号是否出现"代替"读实现"**，且**每轮扫描的候选集不完整**。
→ **可迁移规则：判定"某功能是否存在"时，必须扫全部候选实现并读关键实现体，不能只看一个函数名或一次 grep。**

## 五、影响评估

| 影响 | 说明 |
|:---|:---|
| **数据质量 100% 依赖上游** | 本项目的"清洗"只保证**能写入**，不保证**正确**。上游返回脏数据（异常价、重复行、缺失值）会**原样入库** |
| **`null → 0` 填充是一个隐患** | `_preprocess_records` 支持 `fill_numeric` 把 `None` 填成 `0` —— **若对价格列使用，会制造出"0 价"假数据**（本次退市股回填时我正是踩到同类问题：`area`/`industry` 被 pandas 变成 `0.0`）。**需核查哪些表用了 `fill_numeric`** |
| **`sync_index_weight` 无清洗** | 该表仅指数权重，风险较低，但属唯一缺口 |
| **门 2（正确性）未实现** | 与 `01_数据质量标准.md` §〇 的记载一致，非本次新增 |

## 六、验证结果（2026-09-19）

### 验证①：`fill_numeric` 从未被使用 → **污染风险排除** ✅

```
fill_numeric 的全部命中（3 处）：
  sync_service.py:434   def _preprocess_records(..., fill_numeric=())
  sync_service.py:441       fill_numeric: 需将None→0的数值字段     ← docstring
  sync_service.py:458       for field in fill_numeric:             ← 实现体
```
**三处全是它自身的定义/文档/实现，没有任何调用方传参。** 默认值 `()` → 不填充。
→ **无价格/量额列被 `None → 0` 污染。**

> **没有质量清洗暂未造成可见损害** —— 故接线 `clean_invalid_data` 的**紧急度下调**。
