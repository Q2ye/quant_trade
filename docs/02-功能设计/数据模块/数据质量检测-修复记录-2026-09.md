## 一、修复前的三处问题

### 问题①（最严重）：同步触发路径 **50/53 空转**

```
data_quality_checks 共 53 种 data_type：
  ✅ 质量服务认识的   3 种：all / daily_quotes / stock_list
  ❌ 质量服务不认识的 50 种：adj_factor / daily_basic / etf_daily / cpi / dividend / ...
```

**根因是两套命名不通**：

```python
# handlers.py:2832  同步完成后触发 —— 传的是【同步类型】
await quality_service.check_data_quality(data_type=dt.value ...)
                                        # adj_factor / daily_basic / etf_daily / ...

# quality_service.py:209-214  只认 3 个【类别名】
if data_type in ("daily_quotes", "all"): ...
if data_type in ("stock_list", "all"): ...
if data_type in ("factor_data", "all"): ...
```

**50 种一个都不匹配 → `metrics` 全 0 → 写入 0 分记录。**
即每次同步后都"检查"了，但**什么也没查**；且 **0 分会让人误读为"质量很差"**。

### 问题②：`total_records` 一列混了三种量纲

| 来源 | 实际含义 | 典型值 |
|:---|:---|---:|
| `stock_list` | 股票只数 | 5,856 |
| `daily_quotes` | **平均每股覆盖天数** | 21.97 |
| `factor_data` | 因子记录数 | 0 |

```python
# _check_daily_quotes_quality（修复前）
"total_records": integrity_result.get("actual_data_days", 0)   # ← 天数当记录数
"valid_records": int(actual_data_days * quality_score)         # ← 天数 × 覆盖率，无意义
```
真实记录数其实查出来了（`data_quality.total_records`），**但被丢弃**。

### 问题③：`all` 模式被覆盖 → 返回 0

三个检查都用 `metrics.update()` **无条件覆盖而非累加** →
`daily_quotes` 设 21.97 → `stock_list` 覆盖为 5856 → `factor_data` 覆盖为 0
→ **`all` 最终 total = 0**。

## 二、修法

### 修复①：质量侧适配同步类型（按"以同步为准"）

**新增单一来源映射**（`modules/data/constants.py`，与 `SUPPORTED_DATA_TYPES` 同处）：

```python
class DataSource:
    SUPPORTED_DATA_TYPES = {...}          # 权威同步类型清单（TUSHARE 41 种）
    DATA_TYPE_TABLE_MAP = {               # 2026-09-19 新增
        "stock_list": "stock_basic",
        "daily_quotes": "stock_daily",
        "adj_factor": "stock_adj_factor",
        "daily_basic": "stock_daily_basic",
        ...                               # 共 55 项
    }
```

**`quality_service` 改为两条路**：

| 路径 | 适用 | 行为 |
|:---|:---|:---|
| `special` | `stock_list` / `daily_quotes` / `factor_data` / `all` | 走原有**专用检查** |
| `generic` | 其余同步类型 | 按映射定位到表，走**通用表级完整性检查** |
| 都不匹配 | 如 `tick_quotes`（无对应表） | **明确跳过、不写记录**（不再写 0 分） |

**新增 `_check_generic_table_quality`**：表存在 / 记录数 / `ts_code` 空值 / 日期覆盖。
**只做完整性**（各表列差异过大），结果里显式标注 `coverage="completeness_only"` ——
避免把"只查了完整性"误读为"正确性也过关"。

### 修复②：量纲

```python
metrics["total_records"] += int(_dq.get("total_records", 0))          # 真实记录数
metrics["valid_records"] += max(_total - _null_close, 0)
metrics["invalid_records"] += _null_close
metrics["coverage_days"] = integrity_result.get("actual_data_days")   # 天数单独存
```

### 修复③：累加

三个检查的 `metrics.update({...})` 全部改为 `metrics[...] +=`；
`daily_quotes` 的异常分支**不再把计数清零**（累加语义下清零会抹掉前序检查）。

## 四、⚠️ 附带发现：`COUNT(*) FILTER` 在压缩 hypertable 上会报错

新增通用检查时踩到：

```sql
SELECT COUNT(*) AS n, COUNT(*) FILTER (WHERE ts_code IS NULL) AS nc FROM stock_daily_basic
→ asyncpg.InternalServerError: unexpected column type 'character varying'
```

**隔离结果**：

| 查询 | `stock_daily` | `stock_daily_basic`（**压缩 hypertable**） |
|:---|:---|:---|
| `COUNT(*)` | ✅ | ✅ |
| `COUNT(1)` | ✅ | ✅ |
| **`COUNT(*) FILTER (...)`** | ✅ | ❌ **报错** |

**改为等价的 `COUNT(*) - COUNT(ts_code)`**（总数 − 非空数 = 空值数），
已在 `stock_daily` / `stock_daily_basic` / `stock_moneyflow` / `stock_adj_factor` 上验证通过。

> **可迁移教训**：本项目大量表是 TimescaleDB hypertable（部分压缩），
> **`FILTER` / 聚合的某些形式在压缩块上会触发 asyncpg 类型解码错误**。
> 写跨表通用查询时优先用**基础聚合的差**，而不是 `FILTER`。
