## 五、⚠️ 必须随结论一起读：**Tushare `suspend_d` 的历史查询不可复现**

### 现象

回填后库内有 **150 条 (ts_code, date)** 是**本次拉取没有、但库里已有**的：

```
库内多出 150 条，日期范围 2026-05-08 ~ 2026-07-02（29 个日期）
样例：000638.SZ 2026-06-03 / 06-04 / 06-05 ； 002231.SZ 2026-05-08 ~ 05-18
```

### 排查（三步，均实测）

| 假设 | 检验 | 结果 |
|:---|:---|:---|
| ① 时区差一天位移 | 检查多出项能否对上原始数据的 ±1 天 | **仅 4/150** → ❌ 排除 |
| ② 分块遗漏 | 每块均 < 5,000，无截断 | ❌ 排除 |
| ③ **API 事后查询不返回** | **直接窄窗问 Tushare** | ✅ **坐实** |

**③ 的直接证据**（同一接口，只改窗口）：

```
2026-06-01~06-10  →  000638.SZ 在: ['06-01', '06-02']
2026-06-03~06-05  →  000638.SZ 在: []          ← 库里有 06-03/04/05
2026-06-03 单日    →  000638.SZ 在: []
```

### 含义（**重要**）

> **`suspend_d` 的「当日实时拉取」比「事后回溯查询」拿到更多记录。**

这有两条推论：

1. **回填得到的历史是「下界」，不是「全集」。** 2016–2025 段**没有同期快照可比**，
   故**无法验证其完整性**；能测的重叠期（2026-05~07）显示回填比实时少 **0.064%（150/235,649）**。
2. **日终的 30 天滚动窗口不是纯浪费** —— 它捕获了事后查不到的记录。
   ⇒ **§三 的「不做」决定（不改日终窗口）得到正向支持**：应继续保留日终滚动。

> ⚠️ **不得**据本记录声称「停复牌历史已完整」。准确表述是：
> **「2016 起的历史已最大化补齐，且与 `stock_daily` 语义一致（门4）；但其完整性无法被证明，只能给下界。」**
