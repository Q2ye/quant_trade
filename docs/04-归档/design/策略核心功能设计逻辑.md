# 核心功能设计逻辑

> 回答"为什么这样设计"，而不是"设计了什么"

---

## 一、为什么是这三件事，不是两件也不是四件

量化交易的本质是一个**学习循环**：

```
研究 → 执行 → 学习 → 研究 → 执行 → ...
```

拆成三件事而不是两件事（研究+执行），是因为"学习"不够显性时，人会跳过它——回测跑完直接上实盘，亏了不知道为什么，赚了也不知道为什么。把"数据资产化"单独列出来，是强制系统记住每一次决策和每一次结果。

研究不产生数据资产 → 每次迭代从零开始 → 永远在原地打转。
执行不产生数据资产 → 实盘白跑了 → 同样的错误会犯两次。

---

## 二、为什么研究层和执行层必须物理分离

### 反例：研究和执行混在一起会发生什么

```
策略代码直接读 Tushare → on_bar 里实时算因子
  ↓
Tushare 限流 → 策略卡住 → 错过交易窗口
因子计算耗 CPU → 延迟增大 → 信号滞后
回测和实盘用同一份数据 → 回测虚高（look-ahead）
```

### 分离后的设计

```
研究层（离线，批量）               执行层（在线，实时）

factor_data 预计算                 从内存缓存读因子
  ↓                                  ↓
training_service 批量训练           on_bar 只做预测
  ↓                                  ↓
joblib 持久化模型                  模型一次加载到内存
  ↓                                  ↓
backtest_engine 5 年回放           实时 bar → predict → 信号

研究层可以跑 1 小时                  执行层必须在毫秒级响应
研究层可以失败重来                   执行层失败 = 错过交易
研究层可以用全部 CPU                 执行层只需要推理
```

**核心逻辑：把重的东西提前算好，执行时只做轻量操作。**

回测引擎的存在，是为了在执行层上线之前，用历史数据把研究层的产出验证一遍。回测不需要快，但需要真——T+1、涨跌停、滑点、佣金，一个都不能省，否则验证没有意义。

## 三、为什么因子走预计算管线而不是策略内实时计算

### 74 个因子 × 27 只 ETF × 每天 = 1998 次计算

```
实时计算: on_bar 每个 bar → 遍历 74 个因子 → rolling/moving average
  → 需要 250+ 日历史 → 策略启动后前 250 天无法产生信号
  → 每个 bar 都重复计算同样的历史值 → 浪费

预计算: backfill 脚本 → factor_data 表 → on_bar 只做 key-value 查询
  → 策略启动后第 60 天即可产生信号（预热用历史数据）
  → 计算一次，永久复用
  → 不同策略可以共享同一份因子数据
```

**核心逻辑：因子是公共基础设施，不是策略的私有财产。** 新策略只需要在 `feature_sets` 里挑因子，不需要重新计算。

## 四、为什么策略代码存在 DB 里而不是 .py 文件里

### 四个场景说明设计意图

**场景1：实盘策略升级**
```
.py 文件模式: 改文件 → 重启服务 → 所有策略实例一起变 → 风险不可控
DB 模式:      新建策略实例 → 回测 OK → 切换到 running → 旧实例保留可回退
```

**场景2：多策略并行**
```
.py 文件模式: 所有策略读同一份代码 → 参数硬编码在文件里 → 没法个性化
DB 模式:      每个实例 strategies.code 独立 → 参数在 strategy_parameters 表 → 各自独立
```

**场景3：排查问题**
```
.py 文件模式: "上周那个版本的代码是什么？" → 不知道, 被覆盖了
DB 模式:      strategy_versions 表 → 任意时间点的代码和参数快照 → 可复现
```

**场景4：模板迭代不影响实盘**
```
.py 文件模式: 改了文件 → seed_builtin_templates → 模板更新 → ?
DB 模式:      模板更新 OK, 但实盘实例的 code 不受影响 → 安全隔离
```

**核心逻辑：策略代码是资产，需要版本管理和热更新，而不是散落在文件系统里。**

## 五、为什么回测引擎要模拟真实券商而不是做数学计算

### 数学计算（Portfolio-level） vs 事件驱动（Event-driven）

```
数学计算:
  daily_return = weight × (close - prev_close) / prev_close
  问题: 不知道 T+1 限制, 不知道涨跌停买不到, 不知道手续费损耗

事件驱动:
  Day T 产生信号 → Day T+1 撮合成交 → 按开盘价+滑点成交
  → 扣除佣金(万一免五)+印花税+过户费 → 更新持仓
  → T+1 买入部分当天不可卖
```

三个关键差异会导致回测虚高 5-15%：

1. **T+1 延迟**：信号日买入价 ≠ 实际成交价（相差一天的开盘价）
2. **涨跌停成交失败**：涨停买不进、跌停卖不出——数学公式不知道这个
3. **费用累加**：一笔交易 ~0.13% 的费用，1000 笔就是 130%，不是小数目

**核心逻辑：回测的目的是验证策略在真实约束下能否盈利，不是为了产出好看的曲线。** 越像真实券，回测结论越可信。

## 六、为什么资金校验做了三层

不是过度设计——是血的教训。第一版只有一层检查（`estimated > cash` → reject），导致：

```
max_single_weight=1.0 时:
  shares = cash / price / 100 × 100
  estimated = price × shares × (1 + commission) ≈ cash × 1.0001
  → 永远 > cash → 永远被拒
  → 满仓策略零成交
```

三层防护的分工：

| 层 | 职责 | 容错 |
|:---|:---|:---|
| `_validate_order` | 拦截明显不可能的订单（超 1% 不处理） | 宽松 |
| `submit_order` | 计算精确成本，自动缩减数量 | 精确 |
| `match_orders` | 按实际开盘价成交，最终校验 | 兜底 |

**核心逻辑：入口宽松不误杀、中间精确不超支、出口兜底保安全。** 每一层有自己的容错区间，任何一层失效都不会导致负现金。

## 七、为什么行业里"数据资产"是护城河

### 一个具体的例子

```
2026-08-15, ETF 底部 v5 产生信号:
  ts_code=159915.SZ, confidence=0.62, 底部概率, 权重 5%

半年后, 这条信号对应的结果:
  is_executed=true, pnl_outcome=+8.3%

一年后, 你有 1000+ 条这样的记录:
  每条 = (74 个因子值, 模型给了 0.62 分, 实际赚了 8.3%)
  
这就是监督学习的完美样本。
任何新模型都可以在这份数据上训练、验证、对比。
别人有 Tushare 数据、有同样的代码、有同样的算法。
但他们没有"我的策略在过去一年里什么情况下预测对了、什么情况下预测错了"的数据。
```

**核心逻辑：市场数据 + 因子计算 = 任何人都能复制。信号→结果的闭环数据 = 只有你有。**

## 八、三个功能的耦合与解耦

```
            研究
             │
    产生策略版本 + 回测结果
             │
             ▼
            执行
             │
    产生信号 + 成交 + 持仓快照
             │
             ▼
          数据资产
             │
    信号→盈亏闭环 + 版本溯源
             │
             ▼
          回到研究 ← 用真实数据训练下一版模型
```

每个环节的输出是下一个环节的输入。解耦点在于：

- 研究层不依赖执行层（可以离线跑，不需要实盘运行）
- 执行层不依赖研究层的实时计算（因子预计算、模型预加载）
- 数据资产层是执行层的被动输出（不影响执行性能）

**核心逻辑：耦合只在数据层面（通过 DB 表），不在代码层面（不互相 import）。** 任何一个环节可以独立替换，只要数据表的 schema 不变。
