# 量化交易系统审计规则

> 适用项目：QuantitativeTrading/quant_trade
> 版本：v1.0
> 最后更新：2026-06-19

---

## 一、概述

### 1.1 为什么需要审计规则

本项目的代码审查经历了一次系统性失效：

- 共计发现 **14 个 Bug**
- 其中 **12 个（86%）** 在常规代码审查中被遗漏
- 遗漏的 Bug 集中在**数据流一致性**和**跨模块契约**两个维度
- 根本原因：审查标准停留在**代码级正确性**，没有覆盖**数据生命周期**

### 1.2 业界基准

| 来源 | 检测率 | 说明 |
|:---|:---|:---|
| 非正式代码审查 | ~25% | 无 checklist，无流程 |
| 单元测试单独 | ~30% | 覆盖有限 |
| **正式设计审查** | **~55%** | Fagan inspection，结构化 checklist |
| **正式代码审查** | **~60%** | 独立审查人 + checklist |
| **多层组合** | **~95%** | 正式审查 + SAST + 测试 + Beta |

> 数据来源：McConnell (Code Complete), Jones (Software Assessments)

### 1.3 参考标准

本规则综合了以下业界标准：

| 标准 | 适用维度 |
|:---|:---|
| **NASA SARB** (PAT-029/030/031) | 架构设计审查、需求追溯 |
| **OWASP SAMM** | 安全架构验证（3 级成熟度） |
| **C4 Model** (UK Gov Digital Land) | 系统架构分层审查 |
| **SEBI 算法交易审计框架** | 数据完整性、审计轨迹、风控参数 |
| **SIFMA FX 审计指南** | P&L 归因、仓位对账、独立价格验证 |
| **ISO/IEC 5055:2021** | 软件内部质量度量 |

## 二、审计分层模型

```
┌──────────────────────────────────────────────────────────┐
│  设计审计（Design Audit）                                  │
│  ├─ 架构层：模块边界 / 依赖方向 / 通信机制                  │
│  ├─ 数据层：Schema / 数据流 / 存储-读取一致性                │
│  └─ 契约层：API schema / 事件格式 / 前后端字段对齐           │
├──────────────────────────────────────────────────────────┤
│  实现审计（Implementation Audit）                           │
│  ├─ Layer 1: 代码层 — 语法 / 类型 / 边界 / 异常             │
│  ├─ Layer 2: 数据流层 — 写入路径 / 读取路径 / 单源 / 覆盖    │
│  ├─ Layer 3: 契约层 — 跨模块值格式 / API 对齐 / DB 字段      │
│  └─ Layer 4: 运行时层 — 会话安全 / JSONB 兼容 / 轮询 / 日志  │
└──────────────────────────────────────────────────────────┘
```

**核心原则**：设计审计在编码前执行（Plan 阶段），实现审计在编码后执行（Review 阶段）。

## 三、设计审计（Design Audit）

> 触发条件：新增模块、跨模块通信、新增数据表、API schema 变更
> 执行时机：编码前（Plan 模式）

### 3.1 架构层

| # | 检查项 | 依据 |
|:--|:---|:---|
| A1 | 新增模块是否在正确的层级（api / core / shared / modules）？ | 项目依赖方向规则 |
| A2 | 模块间通信是否仅通过 EventEngine？（禁止直接 import） | 项目架构规则 |
| A3 | Engine vs Service 职责是否正确？（Engine 有状态+事件，Service 无状态） | 项目架构规则 |
| A4 | 是否引入了循环依赖？ | NASA SARB Q8 |
| A5 | 新增的 Repository 是否放在正确的 `shared/database/repositories/` 路径下？ | 项目 Repository 规范 |
| A6 | 是否考虑了故障模式？（依赖不可用、数据为空、超时） | OWASP SAMM L2 |
| A7 | 是否有不必要的复杂度？（KISS 原则） | NASA SARB Q10 |

### 3.2 数据层

| # | 检查项 | 依据 |
|:--|:---|:---|
| D1 | 画出每个新增/修改字段的**完整生命周期图**：写入位置 → 存储位置 → 读取位置 | 本次经验教训 |
| D2 | 每个字段是否只有一个写入源？（禁止主表 config + 参数表双写） | 单源原则 |
| D3 | 每个字段是否只有一个读取源？（禁止多源合并覆盖） | 单源原则 |
| D4 | JSONB 字段与关系表的职责边界是否清晰？ | 存储模型规范 |
| D5 | 新增 DB 列是否与 ORM 模型同步？是否需要 migration？ | 数据库规范 |
| D6 | 金融数据精度是否满足要求？（NAV 漂移 < 1e-8，Decimal 而非 float） | SEBI / 机构标准 |

### 3.3 性能层（设计阶段）

> 依据：Sentry Django Perf Review、SQLAlchemy Best Practices、算法复杂度分析

#### 3.3.1 数据库查询模式

| # | 检查项 | 反模式 | 依据 |
|:--|:---|:---|:---|
| P1 | 批量查询是否用了 `WHERE ts_code = ANY(:symbols)` 而非逐只循环？ | `for s in symbols: await db.execute(...)` → N 次 DB 往返 | N+1 检测 |
| P2 | 关联数据是否用了 `selectinload` / `joinedload` 预加载？ | 循环中访问 `.relationship` 触发隐式 lazy load | ORM Eager Loading |
| P3 | 批量写入是否用了 `insert().values([...])` 而非逐条 `add()`？ | `for r in records: session.add(Model(**r))` → N 次 INSERT | Bulk Operations |
| P4 | 是否设了合理的分页限制？（默认 ≤ 100，最大 ≤ 1000） | 全表加载到内存 | 内存安全 |
| P5 | 连接池配置是否合理？（pool_size ≥ 10, pool_pre_ping=True） | 默认 pool_size=5，高并发耗尽 | 连接池规范 |

#### 3.3.2 算法复杂度

| # | 检查项 | 判断标准 | 依据 |
|:--|:---|:---|:---|
| P6 | 是否存在 O(N²) 循环？ | 嵌套遍历全量数据；≥1000 元素时必须优化 | 复杂度分析 |
| P7 | 每日循环中是否存在重复全量扫描？ | `max(items)` / `sum(items)` 在循环内每次 O(N) → 外部 O(1) 追踪 | 本次经验教训 |
| P8 | 排序是否只在必要时执行？（`sort_values` / `sorted`） | DataFrame 加载后多次 `sort_values` → 一次排好 | I/O 优化 |

#### 3.3.3 资源管理

| # | 检查项 | 反模式 | 依据 |
|:--|:---|:---|:---|
| P9 | 大对象使用后是否释放？（DataFrame、缓存 dict） | `_data_cache` 无限增长 | 内存泄漏 |
| P10 | 异步 session 是否及时关闭？（`async with session.begin()`） | `session.close()` 漏调 → 连接池耗尽 | Async 规范 |
| P11 | 文件句柄 / 网络连接是否有 `finally` 释放？ | `open()` 无 `close()` | 资源泄漏 |

### 3.4 契约层

| # | 检查项 | 依据 |
|:--|:---|:---|
| C1 | API 请求 schema 新增字段 → 前端 TypeScript 类型同步？ | 前后端对齐 |
| C2 | API 响应新增字段 → 前端 interface 同步？ | 前后端对齐 |
| C3 | 跨模块传递的枚举/常量值是否格式一致？（大小写、类型） | 本次经验教训 |
| C4 | 事件类型命名是否符合 `{module}.{domain}.{action}.{status}` 格式？ | 项目事件规范 |
| C5 | 错误响应对前端是否可操作？（含具体失败原因，而非 "操作失败"） | 可用性原则 |

## 四、实现审计（Implementation Audit）

> 触发条件：任何代码变更
> 执行时机：编码完成后

### Layer 1 — 代码层（√ 必须执行）

#### 1.1 语法与类型

- [ ] `py_compile` 通过
- [ ] `vue-tsc --noEmit` 无新增错误
- [ ] 类型注解与初始化值一致（禁止 `x: pd.DataFrame = None`）
- [ ] 删除/重命名的方法引用已全部更新

#### 1.2 边界条件

| 场景 | 检查 |
|:---|:---|
| None | `getattr(obj, "field", default)` 而非 `obj.field` |
| 空集合 | `df.empty` 检查后 `.iloc[0]` |
| 除零 | 分母 `> 0` 保护 |
| 负数底数 | `total_return <= -1` 阻断开方 NaN |
| 短序列 | `len() < 2` 跳过 `pct_change`/`std`/`cov` |

#### 1.3 异常处理

| 反模式 | 正确做法 |
|:---|:---|
| `except Exception: pass` | 至少 `logger.warning(...)` |
| 所有异常统一 500 | 区分 ValueError(409)/NotFound(404)/Forbidden(403) |
| `logger.error` 打预期异常 | 预期异常不打印 ERROR 级别 |

### Layer 2 — 数据流层（涉及持久化时必须执行）

#### 2.1 写入路径审计

对变更涉及的**每一个字段**，画出写入路径并检查：

```
字段: benchmark
  request.benchmark → create_task → task.config["benchmark"] → DB ✅
  request.parameters.benchmark → backtest_parameters → DB    ❓ 重复？
```

- [ ] 是否写入了多个存储位置？
- [ ] 写入失败（rollback / except pass）是否导致后续读取拿到不一致数据？

#### 2.2 读取路径审计

```
字段: commission_rate
  DB → task.config → config["commission_rate"]           ← 第一源
  DB → backtest_parameters → config["commission_rate"]   ← 覆盖？
```

- [ ] 是否从多个来源读取？
- [ ] 如果多源合并，覆盖方向是什么？（谁优先级高？）
- [ ] 读取路径与写入路径是否一一对应？

#### 2.3 跨层值格式

```
字段: direction
  策略层 → "long"（小写）
  Broker → "LONG"（大写）
  DB     → "buy" / "sell"
  → 格式不统一，必须归一化
```

- [ ] 枚举值在跨层传递时格式一致
- [ ] DB 存储格式与代码期望格式一致

#### 2.4 查询模式审计

- [ ] 是否存在逐条查询的 N+1 模式？检查 `for` 循环内是否有 `await db.execute()`
- [ ] 批量查询是否用了 `ANY(:symbols)` 或 `IN` 子句？
- [ ] 批量写入是 `insert().values([...])` 还是逐条 `add()`？
- [ ] 循环内是否访问了 ORM `relationship` 属性（触发隐式 lazy load）？
- [ ] 是否有多余的 `sort_values` / `sorted` 调用？

#### 2.5 算法复杂度审计

- [ ] 是否有嵌套循环（O(N²)）遍历全量数据？
- [ ] 每日/每元素循环中是否有 `max()` / `min()` / `sum()` 全量扫描？→ 外部用 O(1) 变量追踪
- [ ] DataFrame 是否有不必要的 `.copy()`（双倍内存）？

### Layer 3 — 契约层（涉及 API 时必须执行）

- [ ] `BacktestCreateRequest` 新增 → `BacktestCreateParams` 同步
- [ ] `to_dict()` 新增 → `BacktestTaskResult` 接口同步
- [ ] 后端字段名 `snake_case` → 前端 `camelCase` 映射正确
- [ ] 错误状态码语义正确（409 未完成 / 422 参数错误 / 500 内部错误）

### Layer 4 — 运行时层（涉及 DB/异步时必须执行）

#### 4.1 数据库会话

- [ ] 异步 session 无并发查询（禁止 `asyncio.gather` 共用同一 session）
- [ ] 后台任务使用独立 session（HTTP 请求 session 在响应后关闭）
- [ ] `commit()` 失败有回滚 + 日志

#### 4.2 JSONB 写入

- [ ] `to_dict()` 输出无 NaN / Inf（PostgreSQL JSONB 拒绝）
- [ ] JSON 字段不超限（超长 equity_curve 可能 > 10MB）

#### 4.3 前端状态

- [ ] 轮询字段在后端持续更新（progress commit 成功？）
- [ ] Loading / Empty / Error / Data 四种状态全覆盖
- [ ] 轮询终止条件全覆盖（completed / failed / cancelled）

#### 4.4 数值稳定性

| 检查项 | 阈值 |
|:---|:---|
| 浮点 NAV 漂移 | < 1e-8 |
| 前复权因子一致性 | 相对误差 < 1e-6 |
| NaN 传播阻断 | 所有 `**` 运算前检查底数 > 0 |

#### 4.5 运行时性能

| # | 检查项 | 依据 |
|:--|:---|:---|
| P12 | 连接池配置是否合理？（`pool_pre_ping=True`, `expire_on_commit=False`） | SQLAlchemy Best Practices |
| P13 | 大结果集是否分批读取？（`chunk_size` / `yield_per`） | 内存安全 |
| P14 | 异步 session 是否及时释放？（`finally: await session.close()`） | 连接泄漏 |
| P15 | 回测结果 JSON 是否可能超大？（>10MB 的 equity_curve 应分页或压缩） | 网络传输 |
| P16 | 前端轮询间隔是否合理？（自适应 2s→30s，而非固定 1s） | 服务端压力 |
| P17 | 前端大数据渲染是否用了虚拟列表/按需加载？（ECharts dataZoom / lightweight-charts） | 浏览器性能 |

## 五、审计执行流程

### 5.1 设计审计（Plan 阶段）

```
EnterPlanMode
  ├─ 步骤 0: 确认变更范围（新增/修改的文件列表）
  ├─ 步骤 1: 执行 §三 设计审计（架构 + 数据 + 契约）
  ├─ 步骤 2: 画出关键字段的数据生命周期图
  ├─ 步骤 3: 输出审计结论 → 等待用户确认
  └─ 步骤 4: 确认后进入 ExitPlanMode
```

### 5.2 实现审计（Review 阶段）

```
ExitPlanMode → 编码
  ├─ 每完成一个文件: Layer 1 快速检查（语法/类型）
  ├─ 全部完成后: Layer 2 数据流追踪（写入→存储→读取）
  ├─ 有 API 变更: Layer 3 契约对齐
  ├─ 有 DB/异步变更: Layer 4 运行时检查
  └─ 输出审计报告（通过项 / 发现问题 / 修复状态）
```

### 5.3 触发矩阵

| 变更类型 | 设计审计 | L1 | L2 | L3 | L4 | 性能 |
|:---|:---|:---|:---|:---|:---|:---|
| 纯逻辑修复（不涉及持久化） | — | ✅ | — | — | — | ✅ |
| 新增/修改配置字段 | ✅ | ✅ | ✅ | — | ✅ | — |
| API schema 变更 | ✅ | ✅ | ✅ | ✅ | — | — |
| DB 查询变更 | ✅ | ✅ | ✅ | — | ✅ | ✅ |
| 批量数据处理（循环/遍历/聚合） | — | ✅ | ✅ | — | — | ✅ |
| 新增异步操作 | ✅ | ✅ | — | — | ✅ | ✅ |
| 新增模块/跨 > 2 模块 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

## 六、数据生命周期追踪模板

对每个涉及持久化的字段，必须填写此模板：

```
字段名: ____________________

=== 写入路径 ===
来源 (request.xxx / 计算生成)
  └─ [函数名] ──→ [存储表.列]  (line: ___)

=== 存储位置 ===
□ task.config (JSONB)
□ backtest_parameters (relation)
□ 其他: _______________

=== 读取路径 ===
[存储位置]
  └─ [函数名] ──→ 变量 config["xxx"]  (line: ___)
  └─ [函数名] ──→ 传入 Engine.run()     (line: ___)

=== 风险检查 ===
□ 单一写入源 (无重复写入)
□ 单一读取源 (无多源合并覆盖)
□ 写入失败有兜底
□ 读取兜底值合理: _______________
```

## 七、检查清单速查

### 设计审计（5 分钟快速检查）

- [ ] 模块放在正确的层级？
- [ ] 数据流画了生命周期图？
- [ ] 枚举/常量值跨层格式一致？
- [ ] API schema 前后端同步？
- [ ] 是否存在 N+1 查询 / 逐条循环的 DB 操作？
- [ ] 连接池配置是否合理？

### 实现审计（10 分钟快速检查）

- [ ] 编译通过
- [ ] `except: pass` 全部改成 `logger.warning`
- [ ] `to_dict()` 无 NaN
- [ ] DB 字段无重复写入/读取
- [ ] 异步无共享 session 并发查询
- [ ] 错误码语义正确（不统一 500）
- [ ] 兜底默认值合理
- [ ] **无 N+1 查询**：循环内是否有 `await db.execute()`？
- [ ] **批量写入**：是否用了 `insert().values([...])` 而非逐条 `add()`？
- [ ] **O(N²) 扫描**：循环内是否有 `max()`/`sum()` 全量遍历？
- [ ] **大对象释放**：是否有未清理的 DataFrame / 缓存？
