# S3 任务拆分规范（拆到能独立验证、独立提交）

> 配套：产物模板 `模板/03-任务.md` ｜ 前置：`02-设计.md` 的影响面表 ｜ 机检 `check_delivery.py check`（任务表 ≤3 文件/行）+ `scope`
> **一句话**：拆分的唯一目的，是让每个 commit **能单独验证、单独回滚、单独解释**。做不到 = 继续拆。
> **出口**：任务表机检 PASS + 范围已声明后，`review` → `approve S3 --yes`（你审批）才允许开始编码。

## 一、什么叫拆对了（四条硬属性）

| 属性 | 判据 | 不满足时 |
|:---|:---|:---|
| **可独立验证** | 每个任务有 1 条能跑的命令（pytest 路径 / 脚本 / curl） | 回 S2：说明设计没给出可观测面 |
| **可独立回滚** | 撤掉这个 commit 后系统仍能启动、测试仍绿 | 合并任务或调整顺序（把契约变更单独成任务） |
| **≤3 文件** | 一行任务列 >3 个路径 | 继续拆；拆不动说明设计把两件事混在一起了 |
| **可独立解释** | 能写出一句 `type(scope): 做了什么`，且不带「顺便」 | 拆开，或砍掉「顺便」的部分 |

> 文件数不是目的，**归因**才是：一次改 15 个文件，回归红了无法判断是哪一处引起的（这正是 `00_交付流程总纲.md` §八 记录的反例）。

## 二、五步算法

1. **抄影响面**：把 `02-设计.md` §影响面 的文件清单原样抄下来（漏一个，后续一定偏差）。
2. **按契约边界分组**：同一次「对外行为变化」的文件放一组（例：router + service + repository 同属「新增温度接口」）；纯文档、纯测试、纯配置各自成组或并入相邻组。
3. **切到 ≤3 文件**：超了就按「先骨架后逻辑」「先后端后前端」「先契约后实现」切开。
4. **给每组写验收命令**：见 §四 对照表；写不出就把该组标记为「不可验证」，回 S2。
5. **排顺序 + 写 commit**：见 §三。

## 三、排序规则（冲突时按此优先级）

1. **先契约，后实现**：接口签名 / 事件名 / 表结构先落地（哪怕返回 mock），后续任务才有稳定靶子。
2. **先共享，后模块**：`shared/` 的工具/Repository 先改，模块层再消费。
3. **先 DDL，后代码**：表/列先加（可空或带默认），代码再读写；否则任务 2 跑起来就报缺列。
4. **先能跑通的窄路径，后补齐**：垂直切片（一条链路端到端）+ 后续扩展，优于水平分层（先写完所有 model 再写所有 api）。
5. **风险高的任务排在前面**：T2 的 DDL / 事件契约变更早做，早暴露；不要留到最后一个 commit。

> 每个任务完成后**必须**跑一次自己的验收命令，绿了再进下一个（不要攒到最后一起跑 —— 那样失败无法归因）。

## 四、验收命令怎么写（按改动类型）

| 改动类型 | 验收命令 | 期望 |
|:---|:---|:---|
| 后端函数/服务 | `cd quant_server && .venv/Scripts/python.exe -m pytest tests/<path> -k <name>` | `N passed`，exit 0 |
| API 路由 | 同上 + `curl http://127.0.0.1:8080/quantTrade/...`（服务已起，带 Bearer） | 200 + 关键字段 |
| 前端页面/组件 | `cd quant_web && npx vue-tsc --noEmit && pnpm test:unit` | 0 error |
| 策略代码 | `cd quant_server && .venv/Scripts/python.exe scripts/backtest/backtest_high_vol_momentum.py`（CWD 必须是 `quant_server/`） | 有交易 / 无 NaN / 收益 ∈ [−95%, +500%]。⚠️ `backtest_etf_bottom.py`、`backtest_small_cap.py` 是独立重实现（不 import 策略类），改这两个策略请用 pytest：`tests/modules/test_strategy/test_bottom_strategy_p1_fixes.py`、`test_microcap_strategy.py` |
| 策略代码同步 DB | `cd quant_server && .venv/Scripts/python.exe scripts/quality/sync_strategy_code.py --diff <ID>` 后 `--apply` | 巡检无分叉（exit 0）。改磁盘 `.py` 不同步 `strategies.code` = 回测/实盘仍跑旧代码 |
| 数据回填/同步 | 回填命令 + `SELECT count(*) ...` | 行数与交易日历一致 |
| 纯文档 | `cd quant_server && .venv/Scripts/python.exe scripts/quality/check_delivery.py check` | PASS |
| 纯脚本/工具 | 脚本自身 `--help` 或 `--dry-run` + 一次真实调用 | 输出符合预期，无副作用 |

禁止把「人工看一眼」写成验收命令；确实只能肉眼的（UI 视觉），写清「看哪里、看什么、截图存 `assets/`」。

## 五、范围声明与偏差

- 任务表定稿后立即声明（仓库根执行，前缀是 **相对仓库根** 的路径）：`cd quant_server && .venv/Scripts/python.exe scripts/quality/check_all.py --declare "quant_server/api/,quant_web/src/views/DataCenter/Market/"`（前缀取自任务表）。
- **新增文件必须先加进任务表再写**；否则 ③ 范围门会拦（这是设计如此，不是误报）。新建文件在任务表**同一行**写「新建」，`check_delivery.py` 才会跳过存在性校验。
- **反引号路径必须真实存在**（相对仓库根或 `quant_server/`，不能含空格）：写错的路径会当场 FAIL —— 这是防止把不存在的文件/路由写进任务表、被下游照抄。命令（含空格）不算路径，不会被校验。
- 偏差记录写进 `03-任务.md` §偏差记录：日期 / 为什么超范围 / 新增文件 / 是否改档。改档要同步 `meta.json` 与 `01-需求.md` §档位。

## 六、反例（本项目真实形态）

| 反例 | 为什么错 | 改法 |
|:---|:---|:---|
| 「1. 重构数据模块 2. 修 bug」 | 任务 1 无验收、文件数远超 3 | 拆成「抽公共函数（带单测）」「改调用方（逐个任务）」「删旧代码」 |
| 「1. 后端全部 2. 前端全部」 | 后端任务 10+ 文件；前后端无法独立验证 | 按接口逐个竖切：一个接口 = router+service+test（≤3），前端单独跟 |
| 「顺便把日志格式也统一了」 | 混入无关变更，回滚牵连 | 单开 T0/T1 REQ |
| 任务里写「完成 API」 | 无验收命令 | 写「`GET /api/x` 返回 200 且字段 y 非空」 |
| 所有任务都不写 commit message | 无法反查 REQ | 每行必须有 `feat(scope): ...`，commit body 带 `REQ-YYYYMMDD-slug` |
