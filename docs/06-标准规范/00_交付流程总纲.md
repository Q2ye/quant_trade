## 一、五阶段

```
 S1 需求澄清 ─► S2 设计 ─► S3 任务拆分 ─► S4 功能测试验证 ─► S5 代码评审 ─► 完成
  01-需求.md     02-设计.md    03-任务.md       04-验证.md        05-评审.md
      │              │              │                 │                │
      │              │              └─ 任务>3文件 ─────┘                │
      │              └────────────── 设计缺陷 ─────────────────── 回 S2 ┘
      └─ 判据写不成命令 → 退回 S1（并记录「为什么现在才想清」）
```

> **每段之间是人工卡口**：机检 PASS → `review`（出复核包）→ `approve`（用户审批）→ 才允许进入下一段。
> 机检通过 ≠ 审批通过；没有审批记录就停在本段（`next` 会明确告诉你「等待审批」）。

| 阶段 | 唯一问题 | 产物 | 出口判据（硬） | 不通过处置 |
|:---|:---|:---|:---|:---|
| **S1 需求澄清** | 做完怎么算成功？ | `01-需求.md` | 每条 AC 可执行（命令/操作 → 期望输出）；有明确非目标；档位已定 | 判据不可测 = 未完成 |
| **S2 设计** | 用什么结构实现？ | `02-设计.md` | 契约 + 依赖方向 + 影响面 + 备选取舍；T2 加回滚方案 | 缺影响面 = 未完成 |
| **S3 任务拆分** | 拆成几个可独立交付的单元？ | `03-任务.md` | 每任务 ≤3 文件、有独立验收命令、有 commit message、有依赖顺序；**范围已声明** | 拆不出 = 设计没想清，回 S2 |
| **S4 功能测试验证** | 做的是不是需求要的？（黑盒） | `04-验证.md` | AC 逐条「操作 + 实际输出 + 结论」；机器门全绿 | 实现错 → 回 S3；**AC 本身错 → 回 S1 并记录判据变更** |
| **S5 代码评审** | 代码本身是否站得住？（白盒） | `05-评审.md` | 按路径规则逐条勾选；发现项带 `文件:行`；给出裁定 | 退回 S3（改代码）/ S2（改设计），禁止口头放行 |

> 写法细则（怎么问、怎么算填对、怎么拆）见 `00-1`~`00-4` 四份作业指导；本文件只管「什么时候、谁、必须产出什么」。

### 1.1 阶段推进 = 审批卡口（唯一推进方式）

| 动作 | 命令（CWD=`quant_server/`） | 说明 |
|:---|:---|:---|
| 看进度 | `check_delivery.py next` | 未完成 → 给「怎么做」；已就绪 → 给「复核 + 审批」命令 |
| 出复核包 | `check_delivery.py review [S1-S5]` | 机检结论 + 复核要点 + 该阶段文件全文（带行号），给人看 |
| 记录审批 | `check_delivery.py approve S1 --yes --note "看过，OK"` | 写 `meta.json.approvals`，`status` 推进到下一段 |

硬规则：

1. **只能顺序审批**：S2 未审批时 `approve S3` 直接拒绝（「不能跳阶段」）。
2. **机检不过不许审批**：内容不全 / AC 缺「→」/ 路径不存在 → `approve` 返回 1，先改文件。
3. **必须带 `--yes`**：不带只提示「先 review」，防止手滑把半成品批过去。
4. 审批记录含时间与备注；`status` 只是派生值，**真相是 `approvals`**。
5. 改了已审批阶段的内容 → 重新 `next`/`review` 复核；历史审批不自动撤销，评审时看时间戳判断是否需要重批。

> **S4 ≠ S5**：S4 对照 `01-需求.md`（黑盒，作者 + 脚本可做）；S5 对照 `02-设计.md` + `rules/`（白盒，查反向依赖、边界、异常吞掉、凭证），**作者不自审**（先例：`.claude/agents/strategy-reviewer.md`），用独立只读 agent 或新会话执行。

## 四、产物与命名（唯一存放）

```
docs/09-交付记录/
  INDEX.md                     # REQ 总表（人读）
  .active                      # 当前进行中 REQ 编号（机器读，单行）
  REQ-YYYYMMDD-<slug>/
    meta.json                  # 档位/状态/日期/commits/scope（机器读）
    01-需求.md 02-设计.md 03-任务.md 04-验证.md 05-评审.md
    assets/                    # 截图、SQL 结果、回测日志
```

- **命名即状态**：`01..05` 前缀 = 阶段顺序，缺哪个文件就是卡在哪一步。
- **一个 REQ 一个目录**：过程记录不散落，不与 `02-功能设计/`（长期真相源）混放。
- **meta.json**：`{"req":"REQ-...","tier":"T1","status":"S3","created":"2026-11-08","commits":[],"scope":[],"approvals":{"S1":{"at":"2026-11-08 10:20","note":"看过，OK"}}}`
  - `status` 是派生值（= 第一个未审批阶段），**推进阶段只能由 `approve` 写**；
  - `approvals` 才是审批真相：键为 S1–S5，值含审批时间与备注，缺键 = 该阶段未审批。
  - **旧单兼容**：流程上线前创建的 REQ 没有 `approvals` 键，按旧 `status` 读阶段（`status` 列显示「旧单」）；首次 `approve` 会自动写入 `approvals` 并接管推进。

## 六、例外处置（唯一允许打断流程的三件事）

| 情况 | 动作 | 落点 |
|:---|:---|:---|
| **计划偏差**（发现要动规划外文件） | 暂停，出《偏差说明》：现状 / 原因 / 新增影响 / 是否改档 | 追加到 `03-任务.md` 末尾「偏差记录」 |
| **需求变更**（用户中途改） | 暂停，改 `01-需求.md` 的 AC 并在「判据变更」记时间与理由 | `01-需求.md` |
| **回退代码** | 先说明原因并取得确认，再操作 | `05-评审.md` |

> 判据变更不记 = S1 白做：事后无法区分「实现错了」还是「判据漂了」。

**已知反例（本流程要防的具体失效）：**

|:---|:---|:---|
| 判据后置（先做再想怎么验收） | 验收随结果漂移 | S1 退出判据：AC 必须可执行 |
