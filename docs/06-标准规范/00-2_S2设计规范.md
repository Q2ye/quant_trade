# S2 设计规范（写什么、查到什么程度）

> 配套：产物模板 `模板/02-设计.md` ｜ 流程位置见 `00_交付流程总纲.md` §一 ｜ 知识来源：`.claude/skills/quantsys-architect/`、`.claude/rules/frontend.md`
> **一句话**：设计不是「打算怎么做」，而是**让 S3 能拆、让 S5 能对照**的那份说明。拆不动 = 设计没想清。
> **出口**：机检 PASS 后须 `review` → `approve S2 --yes`（你审批）才进 S3；审批前 S3 不得开工。

## 一、设计的三个读者

| 读者 | 他要从设计里拿到什么 | 拿不到的后果 |
|:---|:---|:---|
| S3 拆分者（可能是你自己） | 文件级影响面 + 契约边界 | 拆出「一次改 15 个文件」的任务 |
| S5 评审者（独立 agent） | 契约原文 + 依赖方向 + 已知取舍 | 评审只能看「代码顺不顺眼」，退回无效 |
| 三个月后的你 | 为什么这么改、当时否掉了什么 | 同样的坑再踩一次，或不敢改 |

## 二、必答六问（对应模板六节）

### 2.1 契约：入口 / 输入 / 输出 / 错误码 / 兼容性

- **入口**写具体：`GET /quantTrade/market/dashboard/temperature`（`api/main.py:205` 定前缀）、事件类型 `risk.check.requested`（`modules/risk/events/risk_events.py:18`）、函数签名 `async def get_market_temperature(session: AsyncSession) -> Dict[str, Any]`。
- **事件名照抄既有事件类**：实际是 3–4 段，如 `risk.check.requested`（无 status 段）、`risk.signal.violation.detected`（4 段）。不要自造第 5 段或换词序，订阅方是按字符串匹配的。
- **输入**写到字段级：字段名、类型、来源（DB 列 / 请求参数 / 上游事件）、可空性。
- **输出**同样字段级；含单位（元 / % / 手）与精度（本项目金额用 `Decimal`，不要 float）。
- **错误码**列全：参数错 400 / 无权限 401·403 / 不存在 404 / 冲突 409 / 内部 500；前端要知道每种怎么展示。
- **兼容性**必须回答三件事：老调用方是否受影响、老数据是否需要回填、是否需要过渡期双写/双读。

### 2.2 数据流与依赖

写成 `A → B → C`，每一步标注**同步调用还是事件**：

```
API router → service（同步）→ Repository（同步）→ DB
trade signal_engine（`signal_engine.py:269-271`）→ EventEngine.publish(RiskCheckRequestedEvent，`risk.check.requested`) → risk 模块（异步）
```

硬规则（`AGENTS.md` 架构约束，违反即 S5 阻塞）：

| 规则 | 说明 |
|:---|:---|
| 依赖方向 | `modules/ → shared/ → core/` 严格单向；`api/ → shared/` |
| 模块间通信 | 只走 EventEngine 异步事件，**禁止直接 import 其他模块** |
| 事件命名 | `{module}.{domain}.{action}.{status}` |
| Engine vs Service | 有状态继承 `EngineBase`；无状态纯计算用 Service |
| Repository | 一表一仓库，继承 `BaseRepository`，不含业务逻辑 |
| DDL | 只改 `docs/sql/create_table.sql`（无迁移框架，直接执行） |

- **复用**一栏必须真查过：`shared/` 里已有实现就别再写一个（例：`shared/utils/time_utils.py` 的交易日/时间工具、`shared/database/repositories/` 的一表一仓库、`shared/messaging/` 的事件总线）。`core/` 只有 `engines/ events/ exceptions/` 三个包，不要往那里塞工具函数。

### 2.3 影响面：靠检索补齐，不靠回忆

三件套（每次都要跑，把命中写进表格）：

```bash
# ① 事件名 / 函数名 / 类名 的所有引用
grep -rn "RiskCheckRequestedEvent" quant_server --include=*.py
# ② 表名 / 字段名的所有读写
grep -rn "stock_moneyflow" quant_server --include=*.py   # 表名带前缀；grep 裸 moneyflow 会命中 DataType 常量，漏掉真实读表
# ③ 配置项的消费方（改默认值必查）
grep -rn "simulated_trading" quant_server/config.yaml quant_server/modules
```

再加两类容易漏的：

- **前端**：接口字段变了，`quant_web/src/api/` 与 `src/views/` 的消费方要一起改。
- **测试**：`quant_server/tests/` 里对该函数/接口的断言是否需要同步（漏改 → ② 回归门红）。

表格里每行都要有「风险」判断：高 = 影响资金/交易路径或跨模块契约；中 = 单模块行为变更；低 = 文档/等价替换。

### 2.4 备选方案：至少 2 个，且写清「为什么不选」

只写优点不算取舍。必须给出**否掉的具体代价**：

| 方案 | 优点 | 缺点 | 结论 |
|:---|:---|:---|:---|
| A 在 service 内过滤 | 改动小，1 文件 | 每次查询多一次全表扫描；10 年数据下 P95 超 2s | ✅ |
| B 建物化视图 | 查询快 | 需要新增 DDL + 定时刷新任务，跨模块（data 写、market 读） | ❌ 迁移成本高于本次收益 |

> 如果两个方案都「差不多」，说明这个设计不值得做，回 S1 重问价值。

### 2.5 回滚：写「怎么退」，不是「应该能退」

- T0/T1：写 `revert commit` 即可，但要确认**无状态残留**（无 DDL、无写库、无外部副作用）。
- T2 必填：回退步骤 + 判定条件（出现什么就回退）+ 时间窗（多久内必须退完）。
- 有 DDL 时：新列必须可空或带默认值；回滚脚本单独写，先备份受影响表。
